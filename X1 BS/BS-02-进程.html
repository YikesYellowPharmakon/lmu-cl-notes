Folie 3

Was ist ein Prozess?

  • Prozess: Instanziierung eines Programms in einem Ablauf mit einem konkreten Zustand
  • Ablauf
    • Eine Abfolge von Instruktionen, die ausgeführt werden
    • Ein Thread (oder mehrere)
  • Zustand
    • Beeinflusst den Ablauf des Programmes oder wird von ihm beeinflusst
    • Register: Allgemeine, Gleitkomma, Status, Stack, Befehlszeiger / Programmzähler (engl.: instruction pointer / program counter)
    • Adressraum: Heap (Halde), Stack (Stapel), und Programmcode
    • Offene Dateien

Prozess 进程: 一个程序的实例化, 它处在一个执行流程 (Ablauf) 中, 并有具体的状态 (Zustand). 执行流程是一串依次执行的指令, 也就是一个 (或多个) 线程. 状态是影响程序执行、或被程序执行改变的一切: 寄存器 (通用寄存器、浮点寄存器、状态寄存器、栈指针, 以及Befehlszeiger 指令指针 / Programmzähler 程序计数器, 它指向下一条要执行的指令); 地址空间 (Heap 堆、Stack 栈 和程序代码); 打开的文件.

记法: 「进程 = 正在运行的程序 + 它此刻的全部状态」. 只要把这些状态保存下来, 以后原样恢复, 进程就能从停下的地方接着运行, 这是后面上下文切换的基础.

Folie 4

Prozess vs. Programm

  • Programm: Statischer Code und statische Daten
  • Prozess: Dynamische Instanz von Code und Daten
  • Es kann mehrere Prozessinstanzen desselben Programms geben
    • Beispiel: mehrere Benutzer können gleichzeitig ls ausführen

程序和进程的区别: 程序是静态的代码和静态数据 (硬盘上的一个文件); 进程是代码和数据的一个动态实例. 同一个程序可以同时有多个进程, 例如几个用户同时执行 ls: 程序文件 /bin/ls 只有一个, 进程有好几个, 各有各的状态.

Folie 5

Erzeugung eines Prozesses

读图: 下面的圆柱是磁盘上的程序, 只有代码 (Code) 和静态数据 (Statische Daten). 创建进程时, 操作系统把它们装入主存 (Hauptspeicher), 再加上运行时才需要的 Heap 堆 (动态分配的内存, 例如 malloc) 和 Stack 栈 (局部变量、函数调用), 合起来就是一个进程的地址空间. 主存里右边的两个浅色块表示还有别的进程. 左边的 CPU 接下来就从这个进程的入口 (main) 开始执行.

Folie 6

Prozess vs. Thread

  • Thread: Leichtgewichtiger Prozess
    • Ein Ablauf ohne eigenen Adressraum (aber gewissem eigenen Zustand)
    • Ein Prozess kann mehrere Threads enthalten
  • Beispiel
    • Zwei Prozesse können an derselben Speicheradresse (z.B. 0xffe84264) unterschiedliche Werte sehen
    • Zwei Threads sehen an derselben Speicheradresse 0xffe84264 denselben Wert

Thread 线程是「轻量级进程」: 一个执行流程, 没有自己的地址空间 (但有一定的自己的状态, 主要是寄存器和栈); 一个进程可以包含多个线程.

例子说明区别: 两个进程在同一个地址 0xffe84264 上可能看到不同的值, 因为每个进程有自己的地址空间, 同一个地址在不同进程里指向不同的物理内存. 同一进程的两个线程共享地址空间, 在这个地址上看到的是同一个值.

CPU 的虚拟化与受限直接执行
Virtualisierung der CPU · CPU-Leistung erhalten

Folie 7

Virtualisierung der CPU

  • Ziel: Jeder Prozess soll den Eindruck haben, die CPU für sich zu haben
  • Ressourcen lassen sich zeitlich und räumlich aufteilen
  • Vereinfachende Annahme: Ein einzelner Uniprozessor (Single Core)
    • Zeitliche Aufteilung der CPU (Time-Sharing) (Multiprozessoren führen zu zusätzlicher Komplexität)
  • Hauptspeicher (Memory)
    • Räumliche Teilung (später)
  • Festspeicher (Disk)
    • Räumliche Teilung (später)

CPU 虚拟化的目标: 每个进程都觉得 CPU 归自己. 资源可以按时间或按空间分配. 先做一个简化假设: 只有一个单核处理器. 这时 CPU 按时间分配, 叫 Time-Sharing 分时: 几个进程轮流用一小段时间 (多处理器会带来额外的复杂性). 主存和硬盘则按空间分配: 每个进程分到一块 (以后再讲).

Folie 8

CPU-Leistung erhalten

  • Direkte Ausführung
    • User-Prozesse dürfen direkt auf der Hardware laufen (keine Emulation)
    • Betriebssystem erstellt den Prozess und ruft den Startpunkt auf (main())
  • Probleme bei direkter Ausführung?
    • Prozess könnte privilegierte Operationen ausführen, z.B. die Daten anderer Prozesse lesen oder schreiben
    • Prozess könnte nie terminieren (langsam, fehlerhaft, oder bösartig); Betriebssystem muss Prozess unterbrechen können
    • Prozess könnte Zeit durch Warten auf I/O verschwenden; Betriebssystem möchte Ressourcen effizient verwalten und die CPU einem anderen Prozess zuteilen
  • Lösung: Eingeschränkte direkte Ausführung – Betriebssystem und Hardware behalten zu einem gewissen Grad die Kontrolle

虚拟化不能以牺牲性能为代价. 办法是直接执行: 用户进程直接在硬件上运行 (不做模拟, 指令由真实 CPU 执行, 所以快); 操作系统只负责创建进程, 然后调用它的入口 main().

直接执行有三个问题, 正好是这一讲的三个「Problem」: ① 进程可能执行特权操作, 例如读写别的进程的数据; ② 进程可能永远不结束 (慢、有 bug 或恶意), 操作系统必须能打断它; ③ 进程可能在等待 I/O 时白白占着 CPU, 操作系统想把 CPU 交给别的进程. 解决办法: Eingeschränkte direkte Ausführung 受限直接执行 (limited direct execution): 操作系统和硬件在一定程度上保留控制权.

问题 1: 特权操作与系统调用
Problem 1: Privilegierte Operationen · System Call

Folie 9

Problem 1: Privilegierte Operationen

  • Ziel: Sicherstellen, dass ein User-Prozess anderen nicht schaden kann
  • Lösung: Hardware-Unterstützung für Privilege Levels (spezielles Statusbit)
    • User-Prozesse laufen in User Mode (eingeschränkter Modus)
    • Betriebssystem läuft in Kernel Mode (uneingeschränkt)
      • Instruktionen zur Kommunikation mit Geräten
      • Prinzipiell mehrere Privilege Levels möglich
  • Wie kann ein User-Prozess auf Geräte zugreifen?
    • System Calls (Systemaufruf, implementiert vom Betriebssystem)
    • Ändert Privilege Level durch sog. trap Instruktion

目标: 保证一个用户进程不能伤害别的进程. 解决办法是硬件支持的Privilege Level 特权级 (CPU 里一个专门的状态位): 用户进程运行在 User Mode 用户态 (受限模式); 操作系统运行在 Kernel Mode 内核态 (不受限), 只有内核态能执行和设备通信的指令. 原则上可以有更多特权级 (x86 有 0–3 四个 ring, 但常用的只有 0 和 3).

那用户进程怎么访问设备 (例如读文件)? 通过System Call 系统调用: 由操作系统实现的服务, 用户进程用一条所谓的 trap 陷阱指令发起, 这条指令会切换特权级. 关键在于: 用户进程不能随便跳进内核的任意位置, 只能从内核事先指定的入口进去.

Folie 10–16

System Call

read():
   movq $0, %rax       System Call Nummer, Index in Syscall Tabelle

   syscall             Instruktion für System Call (früher als Trap via int 0x80)
  1. P möchte sys_read() aufrufen (z.B. um eine Datei zu lesen) (Folie 10)
  2. P sieht durch den User Mode nur seinen eigenen Speicherbereich. Andere Bereiche (z.B. der Kernel) sind versteckt. Direkter Aufruf von sys_read() ist für P unmöglich (Folie 11)
  3. read(): movq $0, %rax; syscall (Folie 12)
  4. CPU führt bei syscall einen Wechsel zu Kernel Mode aus und springt in einen dezidierten System Call Handler (Linux: entry_SYSCALL_64) (Folie 13)
  5. Kernel-Mode, alles ist erlaubt (Folie 14)
  6. Folgt Verweis zum Code für den gewünschten System-Call. Kann weitere Kernel-Funktionen aufrufen, verwendet prozess-spezifischen Kernel-Stack (Folie 15)
  7. Kernel kann auf User-Speicher zugreifen um direkt einen Lese-Buffer zu füllen. Schließlich return-from-trap (sysret, iret) um zum User-Code zurückzukehren (Folie 16)

以读文件为例, 一次系统调用分七步 (七页动画):

  1. 进程 P 想调用内核里的 sys_read().
  2. 但 P 运行在用户态, 只看得到自己的内存区域, 内核等其他区域对它是隐藏的 (图里 P 的范围用括号标出), 所以 P 不可能直接调用 sys_read().
  3. P 调用 C 库的包装函数 read(), 它只做两件事: 把系统调用号放进寄存器 %rax (read 的编号是 0, 它是系统调用表的下标), 然后执行指令 syscall. 以前 (32 位 x86) 用的是软件中断 int 0x80.
  4. CPU 执行 syscall 时切换到内核态, 并跳到一个固定的系统调用处理入口 (Linux 里叫 entry_SYSCALL_64, 图里的 entry_SC). 入口地址是内核启动时设置好的, 用户进程改不了.
  5. 现在处于内核态, 什么都允许.
  6. 入口代码用 %rax 里的编号查系统调用表 (图里红色的格子), 跳到对应的代码 sys_read. 它可以再调用别的内核函数, 用的是这个进程专属的内核栈, 不是用户栈.
  7. 内核可以访问用户内存, 直接把读到的数据填进进程的读缓冲区 buf (图里的橙色块). 最后用 return-from-trap 指令 (sysret 或 iret) 回到用户态, 从 syscall 的下一条指令继续执行.

为什么安全: 用户进程能控制的只有「调用号」和参数, 能进入内核的唯一入口由内核自己设定, 而且内核会检查参数 (例如 buf 是否真的属于这个进程). 这就是「受限」直接执行.

完整的 x86-64 Linux 调用约定: 调用号放 %rax, 参数依次放 %rdi、%rsi、%rdx、%r10、%r8、%r9, 返回值回到 %rax (出错时是负的错误码). 所以 read(fd, buf, n) 的三个参数在 rdi、rsi、rdx 里. 幻灯片只写了调用号这一条, 是简化.

Folie 17

Was ist privilegiert?

  • Privilegierte Operationen
    • Zugriff auf gesamten Hauptspeicher
    • Disk I/O (Festspeicher)
    • Besondere x86 Instruktionen, z.B. lidt (Adresse von Interrupt Descriptor Table festlegen)
  • Was passiert, wenn ein User-Prozess versucht, eine privilegierte Operation auszuführen?

哪些操作是特权的: 访问整个主存; 磁盘 I/O; 特殊的 x86 指令, 例如 lidt (设置中断描述符表的地址; 谁能改这张表, 谁就能决定中断发生时跳到哪里, 也就控制了整台机器).

用户进程试图执行特权操作会怎样: CPU 不会执行它, 而是产生一个异常 (x86 上是 general protection fault), 这本身也是一种 trap: CPU 切到内核态, 跳进内核的异常处理程序. 内核通常的处理是终止这个进程; 在 Linux 上进程会收到 SIGSEGV 信号, 屏幕上显示 Segmentation fault.

Problem 2: Wie CPU entziehen? · Dispatch-Mechanismus

Folie 18

Problem 2: Wie CPU entziehen?

  • Anforderungen an Betriebssystem für Multiprogrammierung (Multitasking)
    • Mechanismus: Um zwischen Prozessen zu wechseln
    • Policy: Um zu entscheiden, welcher Prozess wann ausgeführt (scheduled) wird
  • Trennung von Policy und Mechanismus
    • Wiederkehrendes Thema in Betriebssystemen
    • Policy: Trifft Entscheidungen um eine Performance-Metrik zu optimieren (später)
    • Mechanismus: System-Code der die Entscheidungen umsetzt (Prozess Dispatcher: heute)

要实现Multiprogrammierung 多道程序 (多任务), 操作系统需要两样东西: 机制, 用来在进程之间切换; 策略, 用来决定哪个进程什么时候运行 (scheduling 调度). 两者要分开, 这是操作系统里反复出现的主题: 策略做决定, 以优化某个性能指标 (下一讲); 机制是执行这些决定的系统代码, 这里是Dispatcher 分派程序 (这一讲).

分开的好处: 换一种调度策略时, 切换进程的底层代码不用改.

2. Frage: Welcher Ausführungs-Kontext muss gespeichert und wiederhergestellt werden?

分派程序在概念上是一个无限循环: 让进程 A 运行一个Zeitscheibe 时间片; 停下 A, 保存它的上下文; 加载另一个进程 A’ 的上下文. 后两步合起来叫 Context-Switch 上下文切换.

由此引出两个问题: ① 进程 A 在 CPU 上运行时, 操作系统并没有在运行, 分派程序怎样重新拿到控制权? ② 要保存和恢复哪些执行上下文?

Folie 20

1. Wie erlangt der Dispatcher die Kontrolle?

Option 1: Kooperatives Multi-Tasking

  • Vertrauen, dass Prozess die CPU durch den Aufruf eines Traps abgibt
    • Beispiele: System Call, Page Fault (Seite aufrufen, die nicht im Hauptspeicher liegt), oder Fehler (Illegal Instruction, Divide by Zero)
    • Spezieller System Call yield()
  • Implementiert in Windows bis 3.11, klassischem MacOS bis Version 9

第一种办法: kooperatives Multitasking 协作式多任务. 相信进程会通过触发一次 trap 主动交出 CPU. trap 的例子: 系统调用; Page Fault 缺页 (访问了一个不在主存里的页面); 错误 (非法指令、除以零). 另外还有专门用来让出 CPU 的系统调用 yield(). Windows 3.11 及以前、经典 Mac OS 9 及以前用的就是这种方式.

Folie 26

1. Wie erlangt der Dispatcher die Kontrolle?

  • Probleme mit dem kooperativen Ansatz?
  • Nachteil: Prozess muss sich selbständig an die Regeln halten
    • Kann die Maschine absichtlich oder durch Programmierfehler dauerhaft blockieren, indem er Traps und I/O Operationen vermeidet
    • Einzige Lösung: Neustart!
  • Wird in modernen Betriebssystemen nicht verwendet
    • Ausnahmen bei sehr einfachen embedded Systemen

协作式的缺点: 进程必须自觉守规矩. 一个进程只要不触发 trap、不做 I/O (例如一个死循环 while (1) {}), 无论是故意的还是 bug, 都能永久霸占机器, 唯一的办法是重启. 所以现代操作系统不再用它, 只有非常简单的嵌入式系统例外.

Folie 27

1. Wie erlangt der Dispatcher die Kontrolle?

Option 2: Präemptives Multitasking

  • Garantiert, dass das Betriebssystem regelmäßig die Kontrolle erlangt
  • Das Betriebssystem wird nach einer festgelegten Zeit automatisch betreten
    • Die Hardware erzeugt einen Timer-Interrupt (CPU oder separater Chip)
    • Entweder regelmäßig (z.B. alle 10ms in einem tickful Kernel) oder nach Bedarf (z.B. bis zum Ende der aktuellen Zeitscheibe des Prozesses in einem modernen tickless Kernel)
  • Der Benutzer darf den Timer-Interrupt nicht maskieren (unterdrücken) können

第二种办法: präemptives Multitasking 抢占式多任务, 它保证操作系统定期拿回控制权. 硬件 (CPU 内部或单独的芯片) 产生 Timer-Interrupt 时钟中断, 到点就自动进入操作系统: 要么固定周期 (例如传统的 tickful 内核每 10 ms 一次), 要么按需设定 (现代 tickless 内核把时钟设到当前进程时间片结束的时刻, 空闲时就不必一直被唤醒, 省电). 关键前提: 用户进程不能屏蔽时钟中断, 屏蔽中断的指令是特权指令.

第二个问题: 进程不运行时, 分派程序必须替它保管上下文. 上下文存在 Process Control Block 进程控制块 (PCB) 里, 也叫 process descriptor; 在 Linux 里就是内核的 task_struct 结构体. PCB 里存: 进程号 PID; 进程状态 (运行、就绪、阻塞); 执行状态 (寄存器、程序计数器 PC、栈指针); 调度优先级; 管理信息 (父进程、子进程); 权限 (能访问哪些资源); 打开的文件 (文件描述符); 还有很多 (见 task_struct 的源码).

保存上下文需要硬件帮忙: 中断发生时, 硬件自动切换到这个进程的内核栈, 并把 PC、状态标志和栈指针存进去. 这几样必须由硬件来存, 因为内核代码一开始运行, 就会改掉它们.

这张时序图把前面几页连起来, 三栏是操作系统、硬件、应用程序, 时间从上往下:

  1. 进程 A 在运行.
  2. 时钟中断到来, 硬件: 把 A 的 PC、SP、标志位存进 A 的内核栈, 切到内核态, 跳到 trap 处理程序.
  3. 操作系统处理 trap: 先把 A 其余的用户态寄存器也存进 A 的内核栈. 然后 (调度策略决定换成 B) 调用 switch(): 把当前的内核寄存器存进 PCB(A), 从 PCB(B) 加载 B 的内核寄存器, 切换到 B 的内核栈, 然后执行 return-from-trap.
  4. 硬件执行 iret: 从 B 的内核栈取出 PC、SP、标志位, 切回用户态, 跳到 B 的程序计数器.
  5. 进程 B 接着上次停下的地方运行.

要点在于有两次保存: 用户态寄存器由硬件 (和 trap 处理程序) 存在进程的内核栈上; 内核态寄存器由 switch() 存进 PCB. 切换的诀窍是 switch 换了内核栈: 从 trap 返回时, 硬件以为自己在「返回 A」, 实际上读的是 B 的内核栈, 于是回到了 B.

问题 3: 慢速 I/O 与进程状态
Problem 3: Langsame I/O

Folie 30

Problem 3: Langsame I/O

  • Wenn ein laufender Prozess eine Operation ausführt, die die CPU nicht benötigt, wechselt das Betriebssystem zu einem Prozess, der die CPU benötigt (Frage der Policy)
    • Z.B.: read() / write() greifen auf langsame Hardware zu
  • Betriebssystem muss den Zustand jedes Prozesses kennen:
    • Laufend (Running): Auf der CPU (nur einer auf einem Uniprozessor)
    • Bereit (Ready): Wartet auf die CPU
    • Blockiert (Blocked): Wartet darauf, dass I/O oder Synchronisation abgeschlossen wird

正在运行的进程如果执行一个不需要 CPU 的操作 (例如 read()、write() 访问慢速硬件), 操作系统就切换到一个需要 CPU 的进程 (换给谁是策略问题). 为此操作系统必须知道每个进程的状态:

  • Laufend 运行 (Running): 正在 CPU 上 (单处理器上同一时刻只有一个).
  • Bereit 就绪 (Ready): 可以运行, 在等 CPU.
  • Blockiert 阻塞 (Blocked): 在等 I/O 或同步完成, 此时给它 CPU 也没用.

读图: 四种转换. Running → Ready: 被调度出去 (例如时间片用完). Ready → Running: 被调度上 CPU. Running → Blocked: 发起 I/O 等. Blocked → Ready: I/O 完成. 注意没有 Blocked → Running 的箭头: I/O 完成后进程只是重新变为就绪, 要等调度器选中才能运行; 也没有 Ready → Blocked, 因为只有正在运行的进程才能发起 I/O.

Folie 31

Problem 3: Langsame I/O

  • Das Betriebssystem muss jeden Prozess im System verfolgen
    • Jeder Prozess wird durch eine eindeutige Prozess-ID (PID) identifiziert
  • Das Betriebssystem verwaltet Warteschlangen (queues) für alle Prozesse
  • Ready-Queue: Alle bereiten Prozesse
  • Event-Queue: Eine logische Warteschlange pro Ereignis
    • z.B. Disk-I/O und Locks
    • Enthält alle Prozesse, die darauf warten, dass das Ereignis abgeschlossen wird
  • Nächstes Thema: Policy, welcher bereite Prozess ausgeführt werden sollte

操作系统要跟踪系统里的每个进程, 每个进程有唯一的进程号 PID. 进程按状态放在Warteschlange 队列里: Ready-Queue 就绪队列 装所有就绪的进程; Event-Queue 事件队列 每种事件一个 (例如磁盘 I/O、锁), 装所有在等这个事件完成的进程, 也就是阻塞的进程. 事件完成时, 操作系统把对应队列里的进程移进就绪队列. 下一讲的主题: 策略, 即从就绪队列里选哪个进程运行.

创建与结束进程
Prozesserstellung · fork / exec · exit / wait

Folie 32

Prozesserstellung

  • Prozesse müssen zur Laufzeit des Betriebssystems erstellt werden
  • Grundsätzlich zwei Wege:
    • Option 1: Einen leeren Prozess von Grund auf vollständig neu erstellen
    • Option 2: Einen bestehenden Prozess kopieren und entsprechend anpassen

操作系统运行期间要不断创建进程. 原则上有两种办法: ① 从零开始建一个全新的空进程; ② 复制一个现有的进程, 再做相应修改.

Folie 33

Option 1: Vollständig neuer Prozess

  • Schritte:
    • Spezifischen Code und Daten in den Speicher laden; leeren Call-Stack erstellen
    • PCB erstellen und initialisieren (so aussehen lassen wie einen Kontextwechsel)
    • Prozess in die Ready-Queue einfügen
  • Vorteile: Keine verschwendete Arbeit
  • Nachteile: Schwierig, den Prozess korrekt einzurichten und alle möglichen Optionen abzubilden
    • Prozessberechtigungen, wohin I/O geschrieben wird, Umgebungsvariablen
    • Beispiele: posix_spawn (Linux, 6 Argumente) oder CreateProcess (Windows, 10 Argumente)

办法 1 的步骤: 把程序的代码和数据装入内存, 建一个空的调用栈; 建立并初始化 PCB, 让它看起来像一个刚被上下文切换出去的进程 (这样分派程序就能用平常的切换代码「切回」它, 不需要特殊处理); 把进程放进就绪队列.

优点: 没有白做的工作. 缺点: 要把进程设置正确、覆盖所有可能的选项很麻烦: 权限、I/O 写到哪里、环境变量…… 所以这类接口的参数很多: posix_spawn 有 6 个参数, Windows 的 CreateProcess 有 10 个.

posix_spawn 是 POSIX 标准的接口, 不只 Linux 有, macOS 等其他类 Unix 系统也有.

Folie 34

Option 2: Prozess klonen und ändern

  • Beispiel: Unix fork() und exec()
    • fork(): Klont den aufrufenden Prozess
    • exec(char *file): Überlagert aktuellen Prozess mit neuem Programm
  • fork()
    • Aktuellen Prozess anhalten und seinen Zustand speichern
    • Kopie von Code, Daten, Stack und PCB erstellen
    • Neuen PCB zur Ready-Queue hinzufügen
  • exec(char *file)
    • Ersetzt die aktuellen Daten- und Code-Segmente durch die in dem angegebenen Executable
  • Vorteile: Flexibel, sauber, einfach
  • Nachteile: Je nach Implementierung kann es ineffizient sein, erst eine Kopie zu erstellen und dann den Speicher zu überschreiben

办法 2 就是 Unix 的 fork() + exec(). fork() 克隆调用它的进程: 停下当前进程并保存状态; 复制代码、数据、栈和 PCB; 把新的 PCB 放进就绪队列. 新进程 (Kindprozess 子进程) 和原进程 (Elternprozess 父进程) 几乎一模一样, 唯一的区别是 fork 的返回值: 父进程里返回子进程的 PID, 子进程里返回 0. exec(file) 用指定可执行文件的代码段和数据段替换当前进程的, 进程还是那个进程 (PID 不变), 但运行的程序换了.

优点: 灵活、干净、简单. 例如在 fork 和 exec 之间, 子进程可以用普通的系统调用改自己的设置 (重定向输出、改权限), 不需要一个有几十个参数的接口. 缺点: 视实现而定, 先复制整个内存再马上覆盖掉可能效率很低.

现代系统用 copy-on-write 写时复制 解决这个低效问题: fork 时并不真的复制内存, 父子进程先共享同一批物理页面 (标为只读), 谁要写某一页时才复制那一页. 紧接着就 exec 的子进程几乎不写, 于是几乎什么都不用复制. 另外, 真实的 C 函数没有单独的 exec, 而是一族函数: execl、execlp、execv、execvp、execve 等 (在 <unistd.h>), 区别在于参数怎么传、是否在 PATH 里找程序. 幻灯片的 exec(char *file) 是简化写法.

Folie 35

exit() und wait()

  • Prozess kann mit exit(int retval) beendet werden
    • Wird auch bei return von main() automatisch aufgerufen
    • Rückgabewert kann Informationen übergeben (Anzeige des letzten Rückgabewertes in der Shell mit echo $? )
    • Üblicherweise gilt ein Rückgabewert von 0 als erfolgreich (entspricht dem C-Makro EXIT_SUCCESS), jeder andere Wert als Fehlercode
  • Kindprozesse bleiben mit ihrem Elternprozess logisch verknüpft
    • Elternprozess kann mit wait() (bzw. waitpid()) auf Beendigung eines Kindprozesses warten
    • Erlaubt, seinen Rückgabewert zu lesen, dieser wird im PCB gespeichert
  • Für einen beendeten Kindprozess wird Statusinformation so lange vorgehalten, bis der Elternprozess wait aufruft
    • Solange bleibt der Kindprozess im Zombie bzw. defunct-Zustand erhalten und belegt noch Platz in der Prozesstabelle des Kernels (für den PCB).
    • Wenn der Elternprozess endet, adoptiert init (PID 1) den Kindprozess und ruft sofort wait() auf

进程用 exit(int retval) 结束; main 执行 return 时也会自动调用 exit, 返回值就是参数. 返回值可以传递信息, 在 shell 里用 echo $? 查看上一个命令的返回值. 习惯上 0 表示成功 (对应 C 的宏 EXIT_SUCCESS), 其他值都是错误码.

子进程和父进程在逻辑上保持关联: 父进程可以用 wait() (或 waitpid(), 可以指定等哪一个子进程) 等待子进程结束, 并读到它的返回值, 这个值存在子进程的 PCB 里. 因此子进程结束后, 内核要一直保留它的状态信息, 直到父进程调用 wait. 在这段时间里, 子进程处于 Zombie 僵尸 (也叫 defunct) 状态: 已经不运行了, 但 PCB 仍占着内核进程表的一个位置. 如果父进程先结束, 子进程由 init (PID 1) 收养, init 会立刻对它调用 wait, 僵尸随即消失.

易错: 僵尸进程不占 CPU 和内存, 只占进程表的一项; 但一个从不调用 wait 的父进程如果不断创建子进程, 会把进程表占满, 最后 fork 失败.

Folie 36

Unix-Shells mit fork / exec (pseudocode)

while (1) {
    char *cmd = getcmd();
    pid_t pid = fork();
    if (pid == 0) {
        // Wir sind im Kindprozess. Hier könnten ggf. stdin/stdout umgelenkt werden.
        // exec überschreibt das aktuelle Programm mit dem neuen und startet es
        exec(cmd);
        // exec kehrt nur bei einem Fehler zurück
        printf("ERROR: Could not execute %s\n", cmd);
        exit(1);
    } if (pid == -1) {
        // fork ist fehlgeschlagen (z.B. zu viele aktive Prozesse)
        printf("ERROR: Fork failed\n");
        exit(1);
    } else {
        // fork hat eine PID zurückgegeben, d.h. wir sind im Elternprozess
        // Warte auf Beendigung des Kindprozesses, der NULL-Parameter ignoriert dessen Status
        wait(NULL);
    }
}

shell 的核心就是这个循环: 读一条命令; fork 出一个子进程; 根据 fork 的返回值分三种情况. 返回 0: 这里是子进程, 这时可以先重定向标准输入输出 (shell 的 >、| 就是在这里实现的), 然后 exec 换成要运行的程序. exec 成功就不会返回 (当前程序已经被替换掉了), 所以 exec 后面的代码只在出错时才执行: 打印错误并以 1 退出. 返回 −1: fork 失败 (例如活动进程太多). 返回正数: 这里是父进程, 返回值是子进程的 PID; shell 用 wait(NULL) 等子进程结束 (NULL 表示不关心它的返回状态), 然后读下一条命令.

我把伪代码换成真实的函数 (execlp、waitpid) 写成一个小程序, 让它运行一条命令 echo hi 和一条不存在的命令:

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

void run(char *cmd, char *arg) {
    pid_t pid = fork();
    if (pid == 0) {
        execlp(cmd, cmd, arg, (char *)NULL);
        printf("ERROR: Could not execute %s\n", cmd);
        exit(1);
    } else if (pid == -1) {
        printf("ERROR: Fork failed\n");
        exit(1);
    } else {
        int status;
        waitpid(pid, &status, 0);
        printf("[parent %d] child %d exited with %d\n", getpid(), pid, WEXITSTATUS(status));
    }
}

int main(void) {
    run("echo", "hi");
    run("no_such_cmd", NULL);
}

在终端里直接运行, 输出是预期的四行:

> ./shell
hi
[parent 73077] child 73078 exited with 0
ERROR: Could not execute no_such_cmd
[parent 73077] child 73080 exited with 1

子进程 exec 成功时, echo 打印 hi 并以 0 结束; 命令不存在时, exec 返回, 子进程打印错误并 exit(1), 父进程读到退出码 1 (WEXITSTATUS 从 status 里取出 exit 的参数).

一个意外: 把输出重定向到文件或管道时 (./shell | cat), 结果多了一行:

> ./shell | cat
hi
[parent 72530] child 72569 exited with 0
ERROR: Could not execute no_such_cmd
[parent 72530] child 72569 exited with 0
[parent 72530] child 72570 exited with 1

第 4 行是父进程第一行输出的复制品, 而且是第二个子进程打印出来的. 原因: printf 不是直接写到屏幕, 而是先放进 C 库在进程内存里的缓冲区; 输出到终端时遇到换行就清空缓冲区, 输出到管道时要等缓冲区满或进程结束才清空. 第二次 fork 时, 第一行还在父进程的缓冲区里, fork 连同缓冲区一起复制给子进程; 子进程 exec 失败后调用 exit, exit 会清空缓冲区, 于是把这行又写了一遍. (exec 成功时缓冲区随旧程序一起被替换, 不会出现重复.) 解决办法是 fork 之前调用 fflush(stdout), 加上之后管道输出也只有四行. 这正说明 fork 复制的是进程的全部内存.

幻灯片小错: 第二个判断写成了 } if (pid == -1) {, 少了 else, 应为 } else if (pid == -1) {. 现在的写法里, 「pid == 0」之后开始了一个新的独立 if 语句. 这里碰巧不影响结果, 因为子进程在第一个分支里要么被 exec 替换, 要么 exit(1), 永远走不到第二个 if; 但如果有人删掉 exit(1), 子进程就会落进 else 分支调用 wait(NULL), 然后自己也开始当 shell.

总结
Zusammenfassung

Folie 37

Zusammenfassung

  • Virtualisierung der CPU
    • Mehrere Prozesse laufen auf derselben CPU
    • Context-Switching vermittelt jedem Prozess den Eindruck, dass er seine eigene CPU hat
  • Direkte Ausführung macht Prozesse schnell
    • Ausführung an wichtigen Punkten eingeschränkt, damit das Betriebssystem die Kontrolle behält
  • Die Hardware bietet umfangreiche Unterstützung für das Betriebssystem:
    • Benutzer- vs. Kernel-Modus
    • Timer-Interrupts
    • Automatisches Speichern von Registern
  • Zum Nachlesen: OSTEP, Kapitel 1 – 6

总结: CPU 虚拟化让多个进程在同一个 CPU 上运行, 上下文切换让每个进程以为自己独占 CPU. 直接执行让进程跑得快; 在几个关键点上加以限制 (系统调用、时钟中断), 操作系统就保住了控制权. 硬件提供了大量支持: 用户态和内核态、时钟中断、自动保存寄存器. 延伸阅读: OSTEP 第 1–6 章 (第 4 章进程, 第 5 章进程 API, 第 6 章受限直接执行).

三个问题和各自的解决办法, 复习时可以对照: 特权操作 → 用户态/内核态 + 系统调用; 进程不交出 CPU → 时钟中断 (抢占); 等 I/O 浪费 CPU → 进程状态 + 就绪队列/事件队列.
