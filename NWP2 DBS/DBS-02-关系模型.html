关系模型概览
Relationales Modell · Überblick

Folie 1–2

Kapitel 2 · Das Relationale Modell

  • 1970 von Edgar F. Codd (IBM) eingeführt
  • 1981 Turing Award („Nobelpreis der Informatik“) für diese Arbeit
  • Grundlage für die meisten Datenbanksysteme (z.B. Oracle, Microsoft SQL Server, IBM DB2, Sybase, Postgres, MySQL)

Eigenschaften:

  • Einfache & einheitliche Datenstrukturen – Relationen (Tabellen)
  • Solide theoretische Grundlage (wichtig später für Anfrageverarbeitung & -optimierung)

Anwendung:

  • Direkt: Erstellung von Relationen (Tabellen) mittels SQL-Befehlen
  • Abgeleitet: aus einem gegebenen Entity-Relationship-Schema

(Foto: Edgar F. Codd.) Codd – „A relational model of data for large shared data banks“, 1970.

Relationales Modell 关系模型由 IBM 的 Edgar F. Codd 在 1970 年提出 (论文《大型共享数据库的关系数据模型》), 他因此获得 1981 年的图灵奖 (常被称为「计算机界的诺贝尔奖」). 今天绝大多数数据库系统都以它为基础, 例如 Oracle、Microsoft SQL Server、IBM DB2、Sybase、PostgreSQL、MySQL.

它的两个特点: ① 数据结构简单统一: 只有一种结构, 即 Relation 关系 (直观地说就是表); ② 理论基础扎实: 关系就是数学上的集合, 所以可以用集合论和逻辑来推理, 这一点到第 3、4 章 (关系代数、关系演算) 和第 10 章 (查询处理与优化) 会用到.

怎样得到关系: 要么直接用 SQL 命令建表 (本章后半部分), 要么从 ER 模式 (实体-联系模式, 第 6 章) 推导出来.

域
Domäne

Folie 3
  • Ist ein Wertebereich (oder Typ)
  • Logische Menge von Werten

Beispiele

  • D1 = Ganzzahl (ℤ)
  • D2 = Zeichenkette (String)
  • D3 = Datum
  • D4 = {rot, gelb, grün, blau}
  • D5 = {1, 2, 3}

Kann eine begrenzte oder unbegrenzte Kardinalität | … | haben:

  • | D1 | = ∞ (Unendliche Menge: z.B. ℤ)
  • | D4 | = 4
  • | D5 | = 3

Domäne 域就是一个值域 (也可以理解为数据类型): 一个属性允许取的所有值组成的集合. 它可以是无限集 (整数 ℤ、所有字符串、所有日期), 也可以是有限集 (四种颜色、{1, 2, 3}).

Kardinalität 基数 | D | 是集合里元素的个数: | D4 | = 4, | D5 | = 3, ℤ 是无限集. 注意「基数」这个词在本章有两个用法: 这里指域的大小, Folie 6 里指关系里元组的个数, 意思都是「集合有多少个元素」.

笛卡尔积
Kartesisches Produkt

Folie 4

Das kartesische Produkt (auch: Kreuzprodukt) ist die Menge aller möglichen Kombinationen von Elementen aus k Mengen

Beispiel (k = 2)

D1 = {1, 2, 3}
D2 = {a, b}
D1 × D2 = {(1, a), (1, b), (2, a), (2, b), (3, a), (3, b)}

Beispiel (k = 3)

D1 = D2 = D3 = ℕ
D1 × D2 × D3 = {(1, 1, 1), (1, 1, 2), …, (1, 2, 1), …}

(Rechts je ein Diagramm: jedes Element von D1 ist mit jedem Element von D2 (bzw. D3) durch einen Pfeil verbunden.)

Kartesisches Produkt 笛卡尔积 (也叫 Kreuzprodukt 叉积): 从 k 个集合里各取一个元素, 按顺序排成 k 元组, 所有可能的组合构成的集合.

例 k = 2: D1 有 3 个元素, D2 有 2 个, 所以 D1 × D2 有 3 · 2 = 6 个有序对. 一般地 | D1 × … × Dk | = | D1 | · … · | Dk |. 例 k = 3 里三个域都是自然数 ℕ, 积是无限集.

易错: 元组是有序的, (1, a) 和 (a, 1) 不是同一个元组; (a, 1) 根本不在 D1 × D2 里, 因为第一个分量必须来自 D1.

关系
Relationales Modell · Relationen

Folie 5

Eine Relation R über einer Sammlung von Mengen (Domänen) D1, D2, ⋯, Dk ist eine Teilmenge des kartesischen Produkts D1 × D2 × ⋯ × Dk

R ⊆ D1 × D2 × ⋯ × Dk

Beispiel (k = 2)

D1 = {1, 2, 3}, D2 = {a, b}
R1 = { } (leere Relation)
R2 = {(1, a), (2, b)}
R3 = {(1, a), (2, a), (3, a)}
R4 = D1 × D2 = {(1, a), (1, b), (2, a), (2, b), (3, a), (3, b)}

  • Endliche und unendliche Relationen (wenn mindestens eine Domäne unendlich ist)
  • In Datenbanksystemen: nur endliche Relationen (unendliche nicht realisierbar)
  • Relation ist eine Menge von n-Tupeln (d1, d2, ⋯, dn) mit di ∈ Di
  • Domänen D1, …, Dn als Spalten einer Tabelle interpretierbar

翻译: 定义在域 D1, …, Dk 上的关系 R 是笛卡尔积 D1 × ⋯ × Dk 的一个子集. 也就是说: 先列出所有可能的组合, 关系从中挑出一部分 (哪些组合在现实中「成立」).

例子里四个关系都是 D1 × D2 的子集: 空集 R1 也是 (空关系, 一张没有行的表); R4 取了全部组合. D1 × D2 有 6 个元素, 所以它一共有 26 = 64 个子集, 即 64 种可能的关系.

如果某个域是无限的, 关系本身也可以是无限的 (例如「所有满足 x < y 的整数对」). 数据库只能存有限的东西, 所以数据库里的关系一定是有限的.

关系的元素叫 Tupel 元组: (d1, …, dn), 第 i 个分量来自 Di. 把每个域看成一列, 每个元组看成一行, 关系就是一张表. (这一页从 k 换成了 n, 指的是同一个数.)

Folie 6

Relationen – (Mathematische) Terminologie

Grad (Stelligkeit)
Für Relation R ⊆ D1 × ⋯ × Dk — k ist Grad (Stelligkeit) der Relation

Kardinalität
Anzahl der Tupel in einer Relation (| R |)

Attribut
Spalte in einer Relation (Tabelle)

Reihenfolge
Relation ist eine Menge von Tupeln → Reihenfolge der Tupel ist nicht definiert:

{(0, a), (1, b)} = {(1, b), (0, a)}

Reihenfolge der Attribute ist jedoch relevant:

{(a, 0), (b, 1)} ≠ {(0, a), (1, b)}

术语含义表格里对应
Grad / Stelligkeit 度 / 元数R ⊆ D1 × ⋯ × Dk 中的 k列数
Kardinalität 基数元组个数 | R |行数
Attribut 属性关系的一个分量位置一列

顺序: 关系是集合, 集合的元素没有顺序, 所以行的顺序没有意义: {(0, a), (1, b)} 和 {(1, b), (0, a)} 是同一个关系. 但每个元组内部是有序的, 所以列的顺序有意义: (a, 0) 和 (0, a) 是不同的元组, 两个关系不相等.

易错: 「度」看列, 「基数」看行, 不要混. 例如 Folie 5 的 R3 度为 2, 基数为 3.

「列的顺序有意义」只对 Folie 9 的有序关系模式成立 (元组按位置访问). 如果按 Folie 9 下半部分的无序关系模式来看, 属性靠名字而不是位置识别, 列的顺序就无关紧要了. 课件在 Folie 11 说两种定义都用; 考试时看题目用的是哪种写法.

Folie 7

Beispiel

StudId = {412, 307, 540}
StudName = {Smith, Jones}
Major = {CS, CSE, BIO}

r ist eine Relation über StudId × StudName × Major:

r = {(412, Smith, CS), (307, Jones, CSE), (412, Smith, CSE)}

三个域分别是学号、姓名、专业. 笛卡尔积有 3 · 2 · 3 = 18 个元组, r 选了其中 3 个, 度为 3, 基数为 3.

值得注意: 学号 412 出现了两次 (Smith 同时读 CS 和 CSE). 作为数学上的关系这完全合法: 两个元组在 Major 上不同, 所以是不同的元素. 但这说明在这个 r 里 StudId 不能当作唯一标识一行的键; 键的概念见 Folie 14 起.

关系模式
Relationenschema

Folie 8

Seien A1, A2, …, Ak Attribute mit Domänen D1, D2, …, Dk:

R(A1 : D1, A2 : D2, …, Ak : Dk) ist Relationenschema

  • Legt den Namen und die Struktur der Relation fest

Beispiel

Student(StudId: number, StudName: string, Major: string)

Eine Sammlung von Relationen-Schemata = relationales Datenbankschema

Relationenschema 关系模式描述一张表的结构: 表名 R, 以及每个属性的名字 Ai 和它的域 Di. 例: 表 Student 有三列, StudId 是数字, StudName 和 Major 是字符串.

多个关系模式合在一起就是 relationales Datenbankschema 关系数据库模式. 这和第 1 章的「模式与实例」对应: 模式是结构 (很少变), 实例是某一时刻存的数据 (经常变).

Folie 9

Geordnetes Relationenschema

  • Relationenschema R ist ein k-Tupel von Domänen (Attributen)
  • Attribute werden anhand ihrer Position im Tupel referenziert
  • Zusätzlich können Attribute benannt werden

R = (A1 : D1, A2 : D2, …, Ak : Dk)

Ungeordnetes Relationenschema

  • Relationenschema R ist eine Menge von Attributen
  • Jedem Attribut Ai ist eine Domäne Di zugeordnet
  • Attribute werden über ihre Namen referenziert

R = {A1, …, Ak}   mit   dom(Ai) = Di, 1 ≤ i ≤ k

关系模式有两种形式化方法:

geordnet 有序ungeordnet 无序
模式是k 元组 (A1 : D1, …, Ak : Dk)属性的集合 {A1, …, Ak}
怎样找到一个属性按位置 (第 1 列、第 2 列 …), 名字可有可无按名字
域怎样给出直接写在位置上用函数 dom(Ai) = Di
元组是有序的值序列从属性名到值的映射 t(Ai)

Beispiel

NameEinwohnerBundesland
München1.578.667Bayern
Bremen691.703Bremen
Passau51.907Bayern

Geordnetes Relationenschema

Schema R = (Name: String, Einwohner: Integer, Bundesland: String)
Instanz r = {('München', 1.578.667, 'Bayern'), ('Bremen', 691.703,
             'Bremen'), ('Passau', 51.907, 'Bayern')}

Ungeordnetes Relationenschema

Schema R = {Name, Einwohner, Bundesland} mit dom(Name) = String,
       dom(Einwohner) = Integer, dom(Bundesland) = String
Instanz t = {t1, t2, t3} mit t1(Name) = 'München', t1(Einwohner) = 1.578.667, ...

同一张城市表用两种方式写:

  • 有序: 模式是三元组; 实例里每个元组按位置写值, 第 1 个是 Name, 第 2 个是 Einwohner (居民数), 第 3 个是 Bundesland (联邦州).
  • 无序: 模式是三个属性名的集合, 域单独用 dom 给出; 每个元组 ti 看成一个函数, 输入属性名, 输出值: t1(Name) = 'München'.

注意德语数字写法: 1.578.667 里的点是千位分隔符, 即 1 578 667 (约 158 万). 在 SQL 里要写成 1578667. 课件在这里把实例记作 t, 在有序写法里记作 r, 指的都是同一个实例.

人口数字只是举例. 若把 Bremen 理解为不来梅市, 它约有 57 万居民; 69 万左右是整个不来梅州 (含不来梅港) 的人口. 表里同时有 Bundesland = Bremen, 这一行容易让人误以为两者是一回事.

Folie 11

Diskussion

Vorteil des geordneten Relationenschemas

  • Kompaktere Schreibweise (z. B. beim Einfügen neuer Tupel)
t3 = ('Passau', 51.907, 'Bayern')
            vs.
t3(Name) = 'Passau', t3(Einwohner) = 51.907, ...

Nachteil des geordneten Relationenschemas

  • Eingeschränkte logische Datenunabhängigkeit (z. B. neue Attribute können nur am Ende eingefügt werden)

⇒ Beide Definitionen sind äquivalent
⇒ In diesem Kurs verwenden wir beide Definitionen

有序模式的优点: 写法紧凑, 插入新元组时只要按顺序写值 (SQL 的 INSERT INTO R VALUES ('Passau', 51907, 'Bayern') 就是这种写法).

缺点: logische Datenunabhängigkeit 逻辑数据独立性受限 (第 1 章: 模式改变时应用程序不必跟着改). 应用若按位置访问列, 在中间插入一个新属性会让后面所有列的位置错开, 所以新属性只能加在末尾. 按名字访问就没有这个问题.

结论: 两种定义等价 (表达能力相同, 可以互相转换), 本课两种都用.

关系实例
Relationeninstanz · oder kurz: Relation

Folie 12
  • Relationeninstanz r(R) eines Relationenschemas kann als Tabelle mit n Spalten und mehreren Zeilen verstanden werden
  • Element t ∈ r(R) wird als Tupel (oder Zeile) bezeichnet
  • Instanz eines Datenbankschemas ist eine Sammlung von Relationen
StudentStudIdStudNameMajor← Relationenschema
123SmithCS
235JonesCSE← Tupel
367MillerCSE

Eigenschaften einer Relation

  • Die Reihenfolge der Zeilen (Tupel) ist irrelevant, z. B.:
    {(0, a), (1, b)} = {(1, b), (0, a)}
  • Keine doppelten Zeilen (Tupel) in einer Relation, z. B.:
    {(0, a), (0, a), (0, a), (1, b)} = {(0, a), (1, b)}

Relationeninstanz 关系实例 r(R) 是模式 R 在某一时刻的具体数据, 通常就简称「关系」. 画成表: 表头 (Student, StudId, StudName, Major) 是模式, 每一行是一个元组. 整个数据库模式的实例就是所有表的实例的集合.

因为关系是集合, 所以有两条性质: ① 行没有顺序; ② 没有重复行: 集合里同一个元素写三次还是一个元素, 所以 {(0, a), (0, a), (0, a), (1, b)} 只有 2 个元素.

这两条是关系模型的性质. 实际的 SQL 表默认是多重集 (Multiset / Bag): 没有主键或 UNIQUE 约束时可以存完全相同的行, SELECT 的结果也会保留重复, 要去重得写 SELECT DISTINCT (第 1 章的例子用过). 课件总结里的「keine Duplikate (Details später)」就是指这一点, 第 5 章 SQL 会细讲.

完整性约束
Integritätsbedingungen

Folie 13

Integritätsbedingungen in einem DBMS sind Regeln und Einschränkungen, die die Korrektheit, Konsistenz und Gültigkeit der Daten in einer Datenbank sicherstellen

  • Müssen für jede (zulässige) Instanz eines Relationenschemas erfüllt sein
    • werden bei der Definition des Schemas angegeben
    • werden vom DBMS bei Änderungen an Relationen überprüft

Wenn das DBMS Integritätsbedingungen überprüft, entsprechen die verwalteten Daten besser der realen Welt, die modelliert werden soll!

Beispiele

  • Primär- und Fremdschlüssel-Bedingungen
  • Eindeutigkeitsbedingungen (Uniqueness)
  • NOT NULL-Bedingungen

Integritätsbedingung 完整性约束: 保证数据正确、一致、有效的规则. 它们是模式的一部分 (建表时写下), 每个合法实例都必须满足; 每次插入、修改、删除时由 DBMS 自动检查, 违反就拒绝这次操作.

好处: 规则只写一次, 由 DBMS 统一守住, 不靠每个应用程序自己检查 (第 1 章里「完整性问题」的解决办法). 例子: 主键和外键约束、唯一性约束、非空约束, 本章后面逐个讲.

键
Schlüssel

Folie 14
  • Tupel müssen eindeutig identifizierbar sein (z. B. zur Referenzierung)
  • Im relationalen Modell werden Schlüssel (eindeutige Identifikatoren) aus Attributen gebildet
  • Konvention: Schlüsselfelder werden unterstrichen dargestellt

Beispiel

元组必须能被唯一识别, 比如别的表要「指向」某一行时. 关系模型里, 这个唯一标识叫 Schlüssel 键, 由一个或几个属性组成. 约定: 键属性加下划线.

例子: 员工表 (MNr 员工号, Nachname 姓, Vorname 名, Abteilung 部门) 和部门表 (AbtNr 部门号, Name 部门名). 上图想表达「Huber 属于 Buchhaltung」这种联系, 但表里没有能用来指向部门的东西. 下图把 MNr 和 AbtNr 定为主键, 员工表的 Abteilung 列就可以存部门号 (01 = Buchhaltung, 03 = Marketing), 通过部门号找到部门. 这种「存另一张表的键」就是后面的外键.

Folie 15

Formale Notation

Eine Teilmenge S der Attribute eines Relationsschemas R (S ⊆ R) ist ein Schlüssel, wenn gilt:

(1) Eindeutigkeit — Keine Instanz von R darf zwei Tupel enthalten, die in allen Attributen aus S übereinstimmen

(2) Minimalität — Es gibt keine echte Teilmenge T ⊂ S, die ebenfalls die Eindeutigkeits-Eigenschaft erfüllt

Superschlüssel

  • Menge S ⊆ R ist ein Superschlüssel, wenn sie lediglich die Eindeutigkeit erfüllt
  • Zum Beispiel ist die vollständige Attributmenge S = R ein (trivialer) Superschlüssel für Relation R

翻译: 属性集 S ⊆ R 是键, 当且仅当:

  1. Eindeutigkeit 唯一性: R 的任何实例里都不能有两个元组在 S 的所有属性上取值相同. (注意「所有」: 两个元组在 S 的部分属性上相同是允许的.)
  2. Minimalität 最小性: S 的任何真子集 T ⊂ S 都不满足唯一性. 也就是说, 从 S 里去掉任何一个属性, 唯一性就丢了.

只满足唯一性、不要求最小的属性集叫 Superschlüssel 超键. 整个属性集 R 总是超键 (平凡超键), 因为关系里没有重复元组. 「lediglich」(仅仅) 的意思是「只要求唯一性」, 不是「不满足最小性」: 每个键也都是超键, 键就是最小的超键.

Beispiel

逐个检查 (课程表: Id 编号, KursNr 课程号, Titel 课名, Semester 学期):

  • {Id}: 1, 2, 3 各不相同 → 唯一; 只有一个属性, 自然最小 → 键.
  • {KursNr}: 012 出现两次 → 不唯一. {Titel}: 「Einführung in die Informatik」出现两次 → 不唯一. {Semester}: WS 2024/25 出现两次 → 不唯一.
  • {Id, KursNr}: 唯一 (因为 Id 已经唯一), 但去掉 KursNr 后 {Id} 仍唯一 → 不最小 → 只是超键.
  • {KursNr, Semester}: 三对 (012, WS 23/24)、(012, WS 24/25)、(013, WS 24/25) 各不相同 → 唯一; 两个单属性子集都不唯一 → 最小 → 键.

所以一个关系可以有多个键. 规律: 键的任何超集都是超键; 判断最小性时只需检查去掉每一个属性后是否还唯一.

只看这三行数据, {Titel, Semester} 也是唯一且最小的 (三对 (Einführung …, WS 23/24)、(Einführung …, WS 24/25)、(Medizinische …, WS 24/25) 各不相同, 单独的 Titel、Semester 都不唯一), 课件没有列出. 它算不算键要看现实语义: 同一学期可能开两门同名课 (不同课程号), 那它就不是键. 这正是 Folie 19 要讲的「键由现实语义决定, 不由当前数据决定」. 考试遇到「列出所有键」时, 按题目给的语义判断, 题目只给数据时要把这类组合也考虑进去.

Zusammengesetzter Schlüssel 复合键: 由多个属性组成的键. 去掉 Id 列以后, 没有任何单个属性是唯一的, 必须把课程号和学期合起来才能确定一行 (同一门课每学期开一次). 两个属性都加下划线, 表示它们合起来是键, 不是各自是键.

Folie 18

Primärschlüssel

  • Es ist wichtig, alle möglichen Schlüssel zu ermitteln ⇒ Menge der Kandidatenschlüssel
  • Wenn es mehr als einen Schlüssel gibt, wird einer davon (vom Designer oder der Datenbankadministrator:in) als Primärschlüssel ausgewählt
  • Für Kandidatenschlüssel, die nicht als Primärschlüssel gewählt wurden, können dennoch Eindeutigkeitsbedingungen definiert werden
  • Hinweis: Es ist oft sinnvoll, einen künstlichen Primärschlüssel (ein einzelnes Attribut ⇒ Surrogatschlüssel) einzuführen, insbesondere wenn Relation häufig referenziert wird
  • 一个关系所有的键合称 Kandidatenschlüssel 候选键. 设计时要把它们全找出来.
  • 从候选键里选一个作为 Primärschlüssel 主键 (由设计者或数据库管理员决定). 下划线标的就是主键.
  • 没被选中的候选键仍然可以加唯一性约束 (SQL 里的 UNIQUE), DBMS 照样保证它们不重复.
  • 常见做法: 加一个人工的单属性主键, 叫 Surrogatschlüssel 代理键, 如 Folie 16 的 Id. 好处是别的表引用它时只要存一列, 而不是复合键的好几列; 自然属性 (如课程号) 改变时也不影响引用.

Semantik von Schlüsselattributen

Eindeutigkeit bezieht sich nicht nur auf die aktuellen Tupel in der Relationsinstanz r

⇒ Semantik der Anwendung in der realen Welt

MitarbNrNameGehalt
001Müller1700 €
002Mayer2172 €
003Huber3189 €
004Schulz2171 €

Im Beispiel wären {MitarbNr}, {Name} und {Gehalt} aktuell jeweils eindeutig — aber es könnten künftig Mitarbeitende mit gleichem Namen und/oder Gehalt auftreten.

键的唯一性不只针对当前存的这几行, 而是针对所有可能的合法实例 (见 Folie 15 的「keine Instanz」). 所以判断键要看现实世界的语义.

例: 员工表 (MitarbNr 员工号, Name 姓名, Gehalt 工资) 当前四行里, 员工号、姓名、工资都各不相同. 但以后完全可能招进第二个 Müller, 或两人工资相同; 只有员工号是公司按规则唯一分配的. 所以只有 {MitarbNr} 是键. 从数据可以否定一个键 (出现重复就一定不是), 但不能证明一个键.

外键
Fremdschlüssel

Folie 20

Ein Fremdschlüssel ist eine Menge von Attributen in einer Relation (→ Kind-Relation), die verwendet wird, um auf ein Tupel in einer anderen Relation zu „verweisen“ (→ Eltern-Relation)

Eigenschaften

  • Muss auf den Primärschlüssel der referenzierten Relation verweisen
  • Fremd- und Primärschlüsselattribute müssen übereinstimmende Domänen haben
  • Notwendig in Relationsschemata, die aus Beziehungstypen abgeleitet wurden

Beispiel

PRODUKTE(Produktname, ...)
LIEFERANTEN(Name, ...)
KUNDEN(Vorname, Nachname, ...)
bietet(Produktname → PRODUKTE, Name → LIEFERANTEN, Preis)
bestellt((Vorname, Nachname) → KUNDEN, Menge, Name → LIEFERANTEN, Produktname →
PRODUKTE)

Fremdschlüssel 外键: 一个关系 (Kind-Relation 子关系, 引用方) 里的一组属性, 用来「指向」另一个关系 (Eltern-Relation 父关系, 被引用方) 里的某个元组.

  • 外键指向被引用关系的主键;
  • 外键属性和对应主键属性的域必须一致 (不能用字符串去引用整数);
  • 从 ER 模型的联系类型 (Beziehungstyp, 第 6 章) 转换来的关系一定需要外键, 因为联系本身就是「连接几个实体」.

例子读法: A → R 表示属性 A 是引用 R 的外键. bietet (供应) 是产品和供应商之间的联系: 哪个供应商以什么价格提供哪个产品. bestellt (订购) 连接三方: 哪个顾客向哪个供应商订了多少某产品. 顾客的主键是 (Vorname, Nachname) 两列, 所以外键也是这两列一起: 复合主键必须用复合外键引用.

在 SQL 里外键不一定要指向主键, 指向任何带 UNIQUE 约束的候选键也可以 (PostgreSQL 中 CREATE TABLE U (k INTEGER PRIMARY KEY, u INTEGER UNIQUE); CREATE TABLE V (r INTEGER REFERENCES U(u)) 可以执行). 课件的「muss auf den Primärschlüssel」是关系模型里的简化说法, 本课按课件记.

设计上还可以想一想: bestellt 分别引用 LIEFERANTEN 和 PRODUKTE, 所以无法保证「这个供应商真的供应这个产品」. 如果要保证, 可以让 (Name, Produktname) 一起引用 bietet.

Folie 21

Fremdschlüsselbedingungen und referenzielle Integrität

  • Eine Fremdschlüsselbedingung ist für ein Tupel erfüllt, wenn entweder
    • einige Werte der Fremdschlüsselattribute NULL sind (d. h. die Referenz ist unbekannt), oder
    • die Werte der Fremdschlüsselattribute als Primärschlüsselwerte eines Tupels in der Elternrelation vorkommen
  • Die Kombination der Fremdschlüsselattribute bildet im Relationenschema oft den Primärschlüssel der Relation, z. B.:
    bietet(Produktname → PRODUKTE, Name → LIEFERANTEN, Preis)
  • Wenn alle Fremdschlüsselbedingungen eingehalten werden, ist die referenzielle Integrität sichergestellt, d. h. es existieren keine defekten Referenzen

一个元组满足外键约束, 当且仅当: 要么外键属性里有 NULL (引用未知, 例如新员工还没分部门), 要么外键值确实是父关系里某个元组的主键值.

联系类关系里, 几个外键合起来常常就是它的主键: bietet 的主键是 (Produktname, Name), 即同一个供应商对同一个产品只有一个报价.

所有外键约束都满足时, 就保证了 referenzielle Integrität 参照完整性: 数据库里没有 defekte Referenz 悬空引用 (指向不存在的行).

「einige Werte … NULL」(只要有一些是 NULL) 对应 SQL 的默认匹配方式 MATCH SIMPLE: 复合外键只要有一列是 NULL, 整个约束就不检查. 实测 PostgreSQL 18: 下文 Folie 28 的表 A 里插入 (…, 4, NULL) 被接受, 尽管 B 里没有 b1 = 4 的行. 要求「要么全 NULL 要么全部匹配」得写 MATCH FULL.

Data Definition Language (DDL)

  • Ermöglicht die Definition nicht nur einer Menge von Relationen, sondern auch zusätzlicher Informationen zu jeder Relation, darunter:
    • das Schema einer Relation
    • die Domänen der Attribute
    • Integritätsbedingungen

DDL 数据定义语言 (第 1 章「数据库语言」里讲过) 不只定义有哪些表, 还定义每张表的: 模式 (列), 各列的域 (类型), 完整性约束, 索引, 以及物理存储结构. 后两项属于课程后半部分 (第 8 章存储结构、第 10 章查询处理).

Folie 23

Definition eines Relationsschemas

CREATE TABLE T (     -- T - Name der Relation
    <a1> <d1> <c1>,   -- Definition des ersten Attributs
    <a2> <d2> <c2>,
    ...
    <ak> <dk> <ck>,   -- Definition des k. Attributs
    <tc1>
)

ai – Name des i-ten Attributs
di – Typ (Domäne) des i-ten Attributs
ci – Optionale Attributbedingung für das i-te Attribut
tci – Optionale Tabellenbedingung (z.B. Primärschlüssel, Fremdschlüssel)

Dies erzeugt ein Relationenschema mit einer zunächst leeren Relation (Instanz)

CREATE TABLE 的骨架: 表名 T, 然后每列一行「列名 ai、类型 di、可选的列约束 ci」, 最后可以加表约束 tci (涉及多列的约束, 如复合主键、外键). 对应关系模型: 列名 = 属性, 类型 = 域. 执行后得到模式和一个空实例, 数据要之后用 INSERT 插入. -- 开头的是 SQL 注释.

Einschränkungen und Integritätsbedingungen in SQL

Folie 25

Definition einfacher Einschränkungen in SQL

Einfache Einschränkungen (Constraints) können direkt nach der Attributdefinition angegeben werden

Beispiele

NOT NULL – Attributwert darf nicht undefiniert sein (in SQL: NULL)
PRIMARY KEY – Attribut ist Primärschlüssel (für nicht-zusammengesetzte Schlüssel)
UNIQUE – Attribut ist Kandidatenschlüssel
DEFAULT w1 – Wert w1 wird als Standard verwendet (sofern kein anderer Wert angegeben wird)
CHECK f – Formel f wird bei jeder Einfügung geprüft (z. B. CHECK A ≤ 100)
REFERENCES t1(a1) – Verweis auf Attribut a1 in Tabelle t1 (Fremdschlüssel)

列约束直接写在列定义后面, 只涉及这一列:

  • NOT NULL: 这一列不能是 NULL (SQL 用 NULL 表示「值未知 / 不存在」).
  • PRIMARY KEY: 这一列是主键. 只适用于单列主键; 复合主键要写成表约束 (Folie 27). 主键隐含 NOT NULL 和唯一.
  • UNIQUE: 这一列是候选键, 值不能重复 (但 NULL 可以有多个).
  • DEFAULT w: 插入时没给这一列的值, 就填 w.
  • CHECK f: 每次插入 (和修改) 时检查条件 f, 不满足就拒绝.
  • REFERENCES t(a): 这一列是外键, 引用表 t 的列 a.

幻灯片小错: CHECK A ≤ 100 是示意写法. 实际 SQL 里条件必须加括号, 且没有 ≤ 符号, 要写成 CHECK (A <= 100). 实测 PostgreSQL 18: CREATE TABLE t (A INTEGER CHECK A <= 100) 报 syntax error; 加括号后正常. Folie 27 同样的例子也是如此. 课件后面的真实例子 (Folie 30 的 CHECK (ects > 0)) 写法是对的.

Folie 26

Standardwerte (DEFAULT)

  • Wenn bei einer INSERT-Anweisung kein Attributwert angegeben wird, kann ein DEFAULT-Wert verwendet werden
  • Wenn kein Standardwert definiert ist, wird automatisch NULL verwendet

Beispiel

CREATE TABLE Assistent (
    PersNr INTEGER PRIMARY KEY,
    Name VARCHAR(80) NOT NULL,
    Abteilung VARCHAR(200) DEFAULT 'Informatik'
);

插入时省略了某列: 有 DEFAULT 就用默认值, 没有就是 NULL (如果这一列又是 NOT NULL, 插入就会失败). 实测 PostgreSQL 18:

INSERT INTO Assistent (PersNr, Name) VALUES (1, 'Meier');
SELECT * FROM Assistent;
-- persnr | name  | abteilung
--      1 | Meier | Informatik
Folie 27

Integritätsbedingungen in SQL

Zusätzliche Integritätsbedingungen können unabhängig von der Attributdefinition angegeben werden

Beispiele

PRIMARY KEY(A1, A2, ...) – zusammengesetzter Primärschlüssel
UNIQUE(A1, A2, ...) – zusammengesetzter Kandidatenschlüssel
FOREIGN KEY(A1, A2, ...) REFERENCES t1(B1, B2, ...) Verweis auf zusammengesetzten Schlüssel in Relation t1
    (Hinweis: Falls (B1, B2, …) weggelassen wird, wird angenommen, dass (A1, A2, …) verwendet wird)
CHECK f – Formel f wird bei jedem Einfügen geprüft (z. B. CHECK A ≤ 100)

Hinweis: SQL unterscheidet nicht zwischen Groß- und Kleinschreibung
(Schlüsselwörter & Bezeichner sind standardmäßig nicht case-sensitive)

表约束写在所有列定义之后, 可以涉及多列: 复合主键 PRIMARY KEY(A1, A2)、复合候选键 UNIQUE(A1, A2)、复合外键 FOREIGN KEY(A1, A2) REFERENCES t1(B1, B2) (A1 对应 B1, A2 对应 B2, 按位置配对)、跨列的 CHECK.

大小写: SQL 关键字和 (不带引号的) 表名、列名不区分大小写, create table 和 CREATE TABLE 一样, Kurse 和 KURSE 是同一张表.

幻灯片错误: 「省略 (B1, B2, …) 时, 默认用 (A1, A2, …)」不对. SQL 标准 (以及 PostgreSQL、DuckDB) 规定: 省略被引用列时, 引用的是表 t1 的主键, 与外键列叫什么名字无关. 实测 PostgreSQL 18: CREATE TABLE P (x INTEGER, y INTEGER, PRIMARY KEY(y)); CREATE TABLE Q (x INTEGER, y INTEGER, FOREIGN KEY (x) REFERENCES P) 后, P 里有一行 (x = 100, y = 1); 插入 Q (1, 0) 成功 (1 匹配 P 的主键 y), 插入 Q (100, 0) 报 violates foreign key constraint, 尽管 P 里有 x = 100. 所以外键 Q.x 引用的是 P.y, 不是同名的 P.x. Folie 31 的 REFERENCES course 正是按主键这种规则写的.

「不区分大小写」只适用于关键字和不加引号的名字. 两种情况区分大小写: ① 字符串常量: PostgreSQL 中 SELECT 'a' = 'A' 结果是 false; ② 加双引号的名字: 建表 CREATE TABLE "Foo" 后, SELECT * FROM foo 报 relation "foo" does not exist.

Folie 28

Schlüsseldefinitionen in SQL

CREATE TABLE A (a1 VARCHAR(1),
                a2 VARCHAR(1),
                a3 VARCHAR(1),
                a4 VARCHAR(1),
                a5 INTEGER,
                a6 INTEGER,
                PRIMARY KEY(a1, a2),
                UNIQUE(a3, a4),
   FOREIGN KEY (a5, a6) REFERENCES B(b1, b2));
CREATE TABLE B (b1 INTEGER,
                b2 INTEGER,
                PRIMARY KEY(b1, b2));
  • Tupel in Relation A ohne gültigen Partner in Relation B sind nicht zulässig
  • Ohne zusätzliche Angaben können Tupel in B, die von Tupeln in A referenziert werden, weder gelöscht noch deren Werte b1, b2 verändert werden

表 A: 主键 (a1, a2), 候选键 (a3, a4), 复合外键 (a5, a6) 引用 B 的复合主键 (b1, b2).

逐行检查 A 的四行:

  • 主键 (a1, a2): (x, y), (y, z), (x, x), (z, z) 互不相同 ✓; UNIQUE (a3, a4): (z, u), (x, v), (y, y), (v, x) 互不相同 ✓.
  • 外键: (1, 2) 和 (2, 3) 在 B 里存在 ✓; (4, 5) 不存在 → 第 4 行违反外键约束, 不允许插入.

第二条: 默认情况下 (不写 ON DELETE / ON UPDATE), B 中被引用的行既不能删除, 也不能改它的键值, 否则 A 里就会出现悬空引用. 实测 PostgreSQL 18:

INSERT INTO A VALUES ('z','z','v','x',4,5);
-- ERROR: insert or update on table "a" violates foreign key constraint "a_a5_a6_fkey"
DELETE FROM B WHERE b1 = 1;
-- ERROR: update or delete on table "b" violates foreign key constraint "a_a5_a6_fkey" on table "a"
UPDATE B SET b2 = 9 WHERE b1 = 2;
-- ERROR: (同上)
DELETE FROM B WHERE b1 = 6;    -- (6, 7) 没有被引用, 可以删除

执行顺序: 幻灯片把 A 写在左边、B 写在右边, 但真正执行时必须先建 B. 先建 A 会失败: PostgreSQL 报 relation "b" does not exist, 因为外键引用的表必须已经存在. 删表时反过来, 先删 A 再删 B.

Folie 29

Das Löschen eines Tupels in B ist nicht möglich, wenn darauf referenziert wird

Alternativen

FOREIGN KEY(a5, a6) REFERENCES B(b1, b2) ON DELETE CASCADE
Löschen eines Tupels in B führt zum Löschen aller referenzierenden Tupel in A

FOREIGN KEY(a5, a6) REFERENCES B(b1, b2) ON UPDATE CASCADE
Änderung eines Tupels in B führt zur automatischen Änderung der referenzierenden Tupel in A

FOREIGN KEY(a5, a6) REFERENCES B(b1, b2) ON DELETE SET NULL
„Herrenlose Referenzen“ in A werden auf NULL gesetzt

默认行为是「拒绝」. 可以改成别的 referenzielle Aktion 参照动作:

写法B 中被引用的行被删除 / 修改时, A 里引用它的行
(不写, 即 NO ACTION)操作被拒绝
ON DELETE CASCADE跟着一起删除 (级联删除)
ON UPDATE CASCADE外键值跟着改成新值
ON DELETE SET NULL外键列设为 NULL (「无主引用」, 引用对象没了)

实测 PostgreSQL 18 (A、B 数据同上, 前三行):

-- 外键加 ON DELETE CASCADE ON UPDATE CASCADE
UPDATE B SET b1 = 5, b2 = 5 WHERE b1 = 2;
-- A 中 (x, x, y, y, 2, 3) 变成 (x, x, y, y, 5, 5)
DELETE FROM B WHERE b1 = 1;
-- A 中引用 (1, 2) 的两行 (x, y, …) 和 (y, z, …) 被一起删除, 只剩 (x, x, y, y, 5, 5)

-- 外键改成 ON DELETE SET NULL, 重新装入数据
DELETE FROM B WHERE b1 = 1;
-- A 中这两行保留, a5、a6 变成 NULL

易错: CASCADE 作用在子表 (A) 上, 触发它的是父表 (B) 的删除或修改. 删 A 的行从来不会影响 B.

课件推荐的 DuckDB 2.0 目前不支持这些参照动作: 建表时写 ON DELETE CASCADE、ON UPDATE CASCADE 或 SET NULL 会报 FOREIGN KEY constraints cannot use CASCADE, SET NULL or SET DEFAULT. 想动手试要用 PostgreSQL (或 SQLite, 需先执行 PRAGMA foreign_keys = ON).

Zusammengesetzter Primärschlüssel { kursname, semester }

CREATE TABLE Kurse (
    kursname VARCHAR(50) NOT NULL,
    semester VARCHAR(50) NOT NULL,
    ects INT CHECK (ects > 0) DEFAULT 6,
    dozent VARCHAR(100) NOT NULL,
    PRIMARY KEY (kursname,semester)

Einfacher Primärschlüssel { kursID }

CREATE TABLE Kurse (
    kursID INTEGER PRIMARY KEY,
    kursname VARCHAR(50) NOT NULL,
    semester VARCHAR(50) NOT NULL,
    ects INT CHECK (ects > 0) DEFAULT 6,
    dozent VARCHAR(100) NOT NULL
);

同一张课程表的两种设计:

  • 上: 复合主键 (kursname, semester), 必须写成表约束. 每列的 NOT NULL 对主键列其实是多余的 (主键本来就不许 NULL), 写上也没错.
  • 下: 加一个代理键 kursID (Folie 18), 主键直接写在列后面. 注意这样一来 DBMS 不再阻止同一门课在同一学期出现两次; 若要保留这个规则, 应再加 UNIQUE (kursname, semester).

ects INT CHECK (ects > 0) DEFAULT 6: 学分必须为正, 不给值时默认 6. 两个版本都已在 PostgreSQL 18 上成功建表.

Folie 31

Tabelle für Dozent:innen

CREATE TABLE lecturer (
    l_id INTEGER PRIMARY KEY,
    name VARCHAR(50),
    birthday DATE);

Tabelle für Beziehung zwischen Dozent:innen und Kursen

CREATE TABLE teaches (
    lecturer INTEGER REFERENCES lecturer(l_id) ON DELETE CASCADE,
    courseId INTEGER NOT NULL,
    semester VARCHAR(20) NOT NULL,
    PRIMARY KEY(lecturer, courseId, semester),
    FOREIGN KEY (courseId, semester) REFERENCES course);

Schlüsselwort ON DELETE CASCADE: Wird ein lecturer-Tupel gelöscht, werden auch alle zugehörigen (referenzierenden) Tupel in der teaches-Relation automatisch gelöscht

teaches (讲授) 是讲师和课程之间的联系表: 列 lecturer 引用 lecturer(l_id) (列名和表名相同, 这是允许的); (courseId, semester) 是引用 course 的复合外键, 省略了被引用列, 所以引用的是 course 的主键. 三个外键列合起来是主键 (Folie 21: 联系表的外键常常组成主键).

ON DELETE CASCADE: 删除一位讲师, 这位讲师的所有讲授记录自动删除. 实测 PostgreSQL 18: 讲师 1、2 都讲课程 (10, 'WS26'), 执行 DELETE FROM lecturer WHERE l_id = 1 后, teaches 只剩 (2, 10, 'WS26'). 课程那一侧没写 CASCADE, 所以被讲授的课程不能直接删除.

幻灯片前后不一致: teaches 引用的表 course 在课件里没有定义. Folie 30 定义的课程表叫 Kurse, 它的主键是 (kursname, semester) 或单列 kursID, 都和 (courseId, semester) 对不上. 按原样执行会报 relation "course" does not exist; 需要先建一个主键恰好是两列 (INTEGER, VARCHAR) 的 course 表, 例如 CREATE TABLE course (courseId INTEGER, semester VARCHAR(20), PRIMARY KEY (courseId, semester)), 之后 teaches 才能建成 (已实测).

Ändern von Tabellendefinitionen in SQL

Folie 32

Löschen einer Tabelle

-- Das Relationsschema t1 und alle Tupel werden geloescht
DROP TABLE t1

Hinzufügen neuer Attribute

-- Neue Attribute werden rechts an die Tabelle angehängt
-- Für bereits existierende Tupel ist der Wert standardmäßig null
ALTER TABLE t1 ADD (<a1> <d1> <c1>, ...)

Löschen von Attributen aus einer Tabelle

ALTER TABLE t1 DROP (<a1>, <a2>, ...)

Ändern von Attributdefinitionen in einer Tabelle

ALTER TABLE t1 MODIFY (<a1> <d1> <c1>, ...)
  • DROP TABLE t1: 删除整张表, 模式和所有数据都没了 (和 DELETE FROM t1 不同, 后者只删行、保留空表).
  • ALTER TABLE … ADD: 加新列, 加在最右边 (Folie 11 说的有序模式「只能在末尾加」); 已有的行在新列里是 NULL (除非给了 DEFAULT).
  • ALTER TABLE … DROP: 删列. ALTER TABLE … MODIFY: 改列的类型或约束.

版本差异: 这一页带括号的 ADD (…)、DROP (…) 和 MODIFY 是 Oracle 的写法, 在标准 SQL、PostgreSQL 和 DuckDB 里都是语法错误 (实测 PostgreSQL 18 三条都报 syntax error, DuckDB 的 ADD (…) 也报错). PostgreSQL / DuckDB 里每次改一列:

ALTER TABLE t1 ADD COLUMN email VARCHAR(80);          -- COLUMN 可省略
ALTER TABLE t1 DROP COLUMN email;
ALTER TABLE t1 ALTER COLUMN name TYPE VARCHAR(100);   -- 改类型

以上三条已实测通过. 多列可以用逗号连写: ALTER TABLE t1 ADD COLUMN x INT, ADD COLUMN y INT.

Komplexes Tabellenbeispiel in PostgreSQL

CREATE TABLE Students (
    StID NUMERIC CONSTRAINT Students_pk PRIMARY KEY,
    FName VARCHAR(50) NOT NULL,
    LName VARCHAR(50) NOT NULL,
    DOB DATE CONSTRAINT dob_check
    CHECK(DOB IS NOT NULL AND to_char(DOB) > '01-JAN-01'),
    Major CHAR(5) CONSTRAINT fk_majors REFERENCES Majors,
    ZipCode INTEGER CONSTRAINT check_zip
        CHECK(ZipCode IS NOT NULL AND ZipCode BETWEEN 1 AND 99999),
    City VARCHAR(50),
    Street VARCHAR(50),
    Started DATE NOT NULL,
    CONSTRAINT dates_check CHECK(DOB < Started),
    CONSTRAINT name_add UNIQUE(FName, LName, DOB)
);

这个例子把本章的约束都用上了. 新东西是 CONSTRAINT 名字: 给约束起名, 违反时报错信息里会出现这个名字, 以后也可以按名字删除约束 (ALTER TABLE Students DROP CONSTRAINT check_zip).

  • StID: 主键, 约束名 Students_pk.
  • DOB (出生日期): 不能为空, 且要晚于 2001 年 1 月 1 日 (本意).
  • Major: 外键, 引用 Majors 表的主键 (省略了列名, 见 Folie 27 的红框).
  • ZipCode (邮编): 不能为空, 在 1 到 99999 之间 (BETWEEN 包含两端).
  • 表约束 dates_check: 出生日期早于入学日期 Started, 涉及两列, 所以写成表约束.
  • 表约束 name_add: (名, 姓, 出生日期) 组合唯一, 是一个候选键.

幻灯片错误: 标题说是 PostgreSQL, 但 to_char(DOB) > '01-JAN-01' 是 Oracle 的写法. PostgreSQL 的 to_char 必须有第二个参数 (格式串), 实测 PostgreSQL 18 建表报 function to_char(date) does not exist. 即使在 Oracle 里, 这也是字符串比较: 日期先转成「DD-MON-YY」文本, 再按字母顺序和 '01-JAN-01' 比, 结果取决于日 (DD) 而不是年份, 并不能表达「晚于 2001-01-01」. 正确写法是直接比较日期: CHECK (DOB IS NOT NULL AND DOB > DATE '2001-01-01'). 这样改后 (并先建好 Majors 表), 整个 CREATE TABLE Students 在 PostgreSQL 18 上执行成功.

总结
Zusammenfassung

Folie 34
  • Relationales Modell bildet theoretische Grundlage relationaler Datenbanksysteme (RDBMS)
  • Operationen auf Relationen folgen der Mengensemantik – d. h. keine feste Reihenfolge und keine Duplikate (Details später)
  • SQL-DDL-Anweisungen ermöglichen die Definition mehrerer Relationen im Rahmen eines relationalen Datenbankschemas
  • 关系模型是关系数据库系统 (RDBMS) 的理论基础: 关系 = 笛卡尔积的子集 = 一张表.
  • 对关系的操作遵循集合语义: 没有固定顺序, 没有重复 (SQL 的多重集语义是例外, 以后细讲).
  • 用 SQL-DDL (CREATE TABLE、ALTER TABLE、DROP TABLE) 定义关系数据库模式里的各个关系, 以及键、外键、NOT NULL、UNIQUE、CHECK、DEFAULT 等完整性约束.

本章考试重点: 度与基数; 键、超键、候选键、主键的区别, 能从一张表判断哪些属性集是键或超键; 外键与参照完整性; 能读写带约束的 CREATE TABLE, 知道默认情况下和 CASCADE / SET NULL 时删除父表行会发生什么.
