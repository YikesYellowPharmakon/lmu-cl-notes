版本控制与 Git
Version control · Git

Slide 3

“Version control [. . . ] is the management of changes to documents, computer programs, large web sites, and other collections of information.” (Wikipedia)

  • tracks changes to files over time
  • possibility to undo and redo changes
  • parallel code development
  • also for writing theses, reports, archiving results from experiments, etc.

Today: basic git concepts using the command line

版本控制就是管理文件随时间的改动. 它解决三件事:

  1. 记录历史: 每一次改动都留下记录, 谁、什么时候、改了什么, 一查就有.
  2. 可以撤销、重做: 改坏了能回到之前任何一个保存过的版本, 不用再存「论文_最终版_真的最终版.docx」.
  3. 并行开发: 几个人同时改同一个项目, 最后再把各自的改动合到一起.

它不只用于代码, 论文、报告、实验结果的存档也一样适用. 这节课用命令行讲 Git 的基本概念, 后面再看 PyCharm 里怎么点按钮完成同样的事.

Slide 4
  • developed in 2005 by Linus Torvalds for the Linux kernel
  • today the standard tool for version control
  • distributed version control
    • every copy of a project contains its complete history
    • works without network access or a central server
  • fast branching and merging
  • Git (the tool on your computer) ≠ GitLab/GitHub (websites that host copies of repositories)

Git 由 Linux 的作者 Linus Torvalds 在 2005 年为 Linux 内核开发, 如今是版本控制的事实标准.

  • 分布式 (distributed): 每一份项目副本都带着完整的历史. 所以没有网络、没有中央服务器, 也能查历史、提交、建分支. 和它相对的是集中式系统 (如 SVN), 那里历史只存在服务器上.
  • 分支和合并很快: Git 的分支只是一个指针 (见 Slide 18), 建一个分支几乎不花时间.
  • Git ≠ GitLab / GitHub: Git 是装在你电脑上的程序; GitLab、GitHub 是托管仓库副本的网站, 方便多人共享. 没有它们, Git 照样能用.

快照与哈希
Git Underlying Ideas

Slide 5
  • with every commit, Git takes a snapshot of all your files
  • efficiency: unchanged files are not stored again, only linked

Git 记录的是快照: 每次提交 (commit), 都相当于给整个项目拍一张照片, 记下这一刻所有文件的样子.

但它不笨: 没改过的文件不再存一遍, 只存一个指向上一版的链接. 看图里的 Version 3: A 和 B 都没改 (虚线), 只有 C 变成了 C2, 所以真正新存的只有 C2.

理解成「每次提交 = 一张完整的照片」很重要: 回到某个版本时, Git 是把那张照片整个还原出来, 而不是一步步倒推改动.

Slide 6
  • most operations in Git only need local files (no internet)
  • every commit is identified by a 40-character hash (SHA-1), e.g., 24b9da6552252987aa493b52f8696cd6d3b00373; the first 7 characters are usually enough: 24b9da6
  • Git generally only adds data: once something is committed, it is very hard to lose it
  • 大部分操作只用本地文件, 因为完整历史就在你电脑上 (分布式).
  • 每个提交都有一个 40 位的哈希值 (SHA-1, 十六进制) 当身份证号. 它由提交的内容算出来, 内容一变, 哈希就变. 平时写前 7 位就够用, 例如 24b9da6, 后面的命令里经常看到这种短编号.
  • Git 基本只「添加」数据: 一旦 commit, 几乎不会丢. 所以经常提交是最好的保险; 还没提交的改动才是真正可能丢的.

文件状态与三个区域
States · Git Areas · Typical Git Workflow

Slide 7

Files in the repository can be in the following states:

  • unmodified / committed: data is safely stored in git’s local database
  • modified: file is changed but not committed yet
  • staged: modified (or new) file is marked to get committed
  • untracked: file is not managed by git

仓库里的每个文件, 在任一时刻处于四种状态之一:

状态意思怎么进入这个状态
untracked 未跟踪Git 不管这个文件新建的文件; 或从 Git 里移除跟踪
unmodified / committed 未修改和最后一次提交一样, 安全地存在本地数据库里提交之后
modified 已修改改过了, 但还没准备提交编辑一个已跟踪的文件
staged 已暂存标记为「下一次提交要带上」git add

图里的四条箭头就是一个循环: 新文件 add 后直接进入 staged; 已跟踪的文件编辑后变成 modified, stage 后变成 staged; commit 之后回到 unmodified; 把文件从 Git 里移除, 它又回到 untracked.

Slide 8–9 · Git Areas, Typical Git Workflow
  • Working directory: your project folder, the files you see and edit
  • Staging area (also: index): what will go into the next commit
  • .git directory (local repository): hidden folder with the complete project history
  1. modify files in the working directory.
  2. stage files: store snapshot in the staging area
  3. commit files: store snapshot of staging area permanently in your Git directory

(Slide 8 和 9 是同一张图, Slide 9 多了三步流程.)

状态对应三个区域:

  • 工作区 Working directory: 你看到、编辑的项目文件夹.
  • 暂存区 Staging area / index: 「下一次提交要装进去的东西」, 像一个打包台.
  • .git 目录 (本地仓库): 项目文件夹里的隐藏文件夹, 存着完整历史. 删掉它, 这个文件夹就不再是 Git 仓库了.

日常就是三步: 改 (工作区) → add (放上打包台) → commit (打包存进历史). 反方向的 checkout 是从历史里把某个版本取出来放回工作区.

为什么要多一个暂存区: 可以只挑一部分改动提交. 比如你同时改了两个功能, 可以先 add 第一个功能的文件提交一次, 再提交第二个, 历史就清清楚楚, 一次提交只做一件事.

配置与建立仓库
Initial configuration · Setting up a Git directory

Slide 10

Git needs a basic configuration to be operational:

  • Username and Email: 
    $ git config --global user.name 'Jon Doe'
$ git config --global user.email 'jon_doe@example.com'
  • (optionally) change default editor: 
    $ git config --global core.editor emacs
  • check your settings: 
    $ git config --list

The settings are stored in the file ~/.gitconfig.

第一次用 Git 先设名字和邮箱: 每个提交都会记下作者, 没设的话 Git 拒绝提交. --global 表示对这台电脑上所有仓库生效, 写进家目录下的 ~/.gitconfig; 不加 --global 就只对当前仓库生效.

core.editor 是需要你写较长说明时 (比如不带 -m 的 git commit) 打开的编辑器, 幻灯片例子是 emacs, 用 VS Code 可以设成 "code --wait". git config --list 列出所有设置.

LMU 的 GitLab 上, 提交显示的作者按这里的邮箱对应账号. 用学校邮箱设置, 作业仓库里才能正确显示是你提交的.

Slide 11
  • turn a local directory into a Git repository: 
    cd dir/to/turn/into/Git
git init
git add .
git commit -m "committing everything in the folder"
  • clone an existing Git repository from elsewhere: With https: 
    git clone https://github.com/username/projectname.git
    With ssh: 
    git clone git@github.com:username/projectname.git

得到一个仓库只有两种方式:

  1. git init: 把现有文件夹变成仓库 (建出隐藏的 .git). 然后 git add . 把文件夹里所有文件放进暂存区 (. 表示当前目录), 再提交一次.
  2. git clone: 把别处已有的仓库连同完整历史复制下来. 地址有 https 和 ssh 两种写法, 区别只在登录方式 (见 Slide 26–27).

日常命令: status、add、commit、rm、mv
git status · git add · git commit · Removing and moving files

Slide 12

Shows what files have been modified/created:

  • after fresh clone: 
    $ git status
nothing to commit, working tree clean
  • after creating a file: 
    $ echo 'My Project' > README
$ git status
Untracked files:
(use "git add <file>..." to include in what will be committed)
README
  • after modifying an existing file: 
    $ git status
Changes not staged for commit:
(use "git add <file>..." to update what will be committed)
(use "git restore <file>..." to discard changes in working directory)
modified:   CONTRIBUTING.md

git status 告诉你每个文件处在 Slide 7 的哪种状态, 是最常用的命令. 三种情况:

  • 刚 clone 完: 工作区和最后一次提交一致, working tree clean.
  • 新建了文件: 列在 Untracked files 下, 括号里还提示下一步用 git add.
  • 改了已跟踪的文件: 列在 Changes not staged for commit 下, 即 modified 状态. 提示两条出路: git add 准备提交, 或 git restore 丢掉这次修改.

Git 的提示信息很有用, 看不懂下一步时先跑一次 git status. 实际输出还会在最前面写 On branch master, 说明你在哪个分支上.

Slide 13

Puts files into the staging area but does not commit them yet:

  • if file is untracked: 
    $ git add README
$ git status
Changes to be committed:
(use "git restore --staged <file>..." to unstage)
new file:   README
  • if file is tracked but was modified: 
    $ git add CONTRIBUTING.md
$ git status
Changes to be committed:
(use "git restore --staged <file>..." to unstage)
modified:   CONTRIBUTING.md

NOTE: git add stages the file as it is now. If you edit it again afterwards, run git add again.

git add 一个命令两种用途: 新文件 add 后开始被跟踪 (new file); 改过的文件 add 后进入暂存 (modified). 两者都出现在 Changes to be committed 下, 也就是 staged.

易错: add 的是文件此刻的样子. add 之后又改了它, 新改动不会自动进暂存区, git status 里这个文件会同时出现在「to be committed」和「not staged」两处. 要再 add 一次.

提示里的 git restore --staged 是仓库已经有提交时的写法 (clone 来的仓库都是这样). 在一个刚 init、一次都没提交过的仓库里, Git 提示的是 git rm --cached <file>, 因为还没有「上一次提交」可以恢复.

Slide 14

Stores a snapshot of the staging area permanently in your .git directory. It only commits what has already been git added.

$ git commit -m "some good description of your changes, e.g.,
fixed case-sensitive bug"

If you want to stage and commit your changes in one step, you do:

$ git commit -a -m 'added new benchmarks'

Careful: -a does not include new (untracked) files. Add them with git add first.

git commit 把暂存区的快照永久存进历史. 只提交 add 过的东西, 没 add 的改动留在工作区不动.

-m 后面是提交说明, 写清楚「这次改了什么」, 例如 fixed case-sensitive bug. 以后翻历史全靠它, 「update」「asdf」这种说明等于没写.

-a 会先把所有已跟踪文件的改动自动 add, 再提交. 易错: 新建的文件 (untracked) 不会被 -a 带上. 实测: 新建 new.txt 后 git commit -am …, 提交完 git status 里它仍是 ?? new.txt.

Slide 15
  • delete a file only in your working directory (git then shows it as “deleted”, not staged): 
    $ rm test.txt
  • usually: delete the file and stage the deletion (older commits still contain the file): 
    $ git rm test.txt
  • rename a file by moving it: 
    $ git mv file_from file_to
    equivalent to: 
    $ mv README.md README
$ git rm README.md
$ git add README
  • 普通的 rm 只删工作区里的文件, Git 看到的是一个「deleted」的改动, 还没暂存.
  • git rm 删文件并且暂存这次删除, 下次提交就记录「删掉了」. 旧提交里仍然有这个文件, 随时能从历史取回.
  • git mv 是改名的简写, 等于「改名 + 删旧名 + 加新名」三步.

分支
Branches

Slide 18
  • a branch is a movable pointer to a commit (not a copy of your files)
  • default branch: master (on GitLab/GitHub: main)
  • HEAD points to the branch you are currently on
  • when you commit, that branch moves forward to the new commit

(图来自 https://git-scm.com/, 箭头从新提交指向它的上一个提交.)

读图: 三个提交排成一条链: 每个提交指向它的上一个提交 (箭头向左), 各自带着一张快照.

  • 分支是一个可移动的指针, 指向某个提交, 不是一份文件副本. 所以建分支几乎不花空间和时间.
  • 默认分支在 Git 里叫 master (实测 git 2.54 的 git init 仍是 master), GitLab、GitHub 上新建仓库默认叫 main. 只是名字不同, 作用一样.
  • HEAD 指向「你当前所在的分支」, 表示「我现在在这里」.
  • 在某分支上提交时, 这个分支的指针前移到新提交, HEAD 跟着它走.

图里的 v1.0 是标签 (tag): 和分支一样是指向提交的名字, 但它固定不动, 用来标记发布版本 (git tag v1.0). 幻灯片正文没讲, 所以这里说明一下.

Slide 19

To create a new branch that points to the same commit HEAD is currently on, use git branch:

$ git branch testing

This does not switch to the new branch: HEAD still points to master.

Slide 20

To switch to another branch, use git checkout:

$ git checkout testing

You can also create a new branch and move HEAD (i.e., checkout) to that branch in one command:

$ git checkout -b testing

建分支和切换分支是两步:

  1. git branch testing: 在 HEAD 所在的提交上新建一个指针 testing. 只建不切, HEAD 还指着 master (Slide 19 的图).
  2. git checkout testing: 把 HEAD 移到 testing (Slide 20 的图). 从此提交会让 testing 前进, master 留在原地.

git checkout -b testing 一次完成「建 + 切」, 最常用.

新版 Git 把 checkout 的两种用途拆成了两个更清楚的命令: 切换分支用 git switch testing (建并切换: git switch -c testing), 恢复文件用 git restore (见 Slide 22). 旧写法照样能用.

Slide 21

To merge the branch testing into master, you have to:

  • switch to the master branch: 
    $ git checkout master
  • merge the branch into your current branch, i.e., into master: 
    $ git merge testing
  • commit all your changes before merging
  • if only testing has new commits: master simply moves forward (fast-forward)
  • if both branches have new commits: git creates a merge commit

合并方向: 先切到「要接收改动」的分支 (master), 再 git merge testing, 把 testing 的改动并进当前分支. 方向搞反是最常见的错误.

合并前先把手头的改动提交掉, 否则 Git 可能拒绝合并, 以免覆盖你的未保存工作.

两种结果:

  • 快进 (fast-forward): master 之后没有新提交, 只有 testing 往前走了. Git 直接把 master 指针挪到 testing 的位置, 不产生新提交. 实测输出 Fast-forward.
  • 合并提交 (merge commit): 两边都有新提交, 历史分了叉. Git 新建一个提交, 它有两个上一个提交 (两个 parent), 把两条线接起来. 实测输出 Merge made by the 'ort' strategy..

两边改了同一处时, 合并会产生冲突, 见 Slide 35.

撤销
Undoing things · git revert · git reset

Slide 22
  • you forgot a file in your last commit: 
    $ git commit -m 'Initial commit'
$ git add forgotten_file
$ git commit --amend
  • you want to unstage a file (your changes stay in the file): 
    $ git add test.txt
$ git reset HEAD test.txt    # newer: git restore --staged test.txt
Unstaged changes after reset:
M        test.txt
  • you want to discard your changes to a file and go back to the last commit (the changes are lost!): 
    $ git checkout test.txt      # newer: git restore test.txt
想做什么命令改动还在吗
上次提交漏了一个文件add 它, 再 git commit --amend在, 并入上一个提交, 不多出新提交
把文件从暂存区拿回来git restore --staged 文件 (旧: git reset HEAD 文件) 在, 文件内容不变, 只是变回 modified
丢掉对文件的修改, 回到最后一次提交git restore 文件 (旧: git checkout 文件) 不在, 没提交过的改动找不回来

输出里的 M test.txt 表示 test.txt 是 modified: 改动还在, 只是不在暂存区了.

易错: --amend 会替换上一个提交 (编号也会变). 已经 push 给别人的提交不要 amend, 原因同下面的 reset.

Slide 23
  • git revert <commit>: new commit (55bfe) that undoes da39a. History is kept, so it is safe after pushing.
  • git reset <commit>: moves the branch back, as if da39a never happened. Only for commits you have not pushed yet.
  • master∼1: one commit before master; master∼3: three commits before.

撤销一个已经提交的改动, 有两种完全不同的思路:

  • revert (反做): 新加一个提交 55bfe, 内容正好抵消 da39a. 历史只增不减, da39a 还在. 别人已经拿到 da39a 也没关系, 所以 push 之后要撤销, 用 revert.
  • reset (回退): 把分支指针往回挪, 好像 da39a 从没发生过. 历史被改写了: 如果别人已经有 da39a, 你们的历史就对不上. 所以只用于还没 push 的提交.

master~1 表示「master 往前数一个提交」, ~3 是往前三个; HEAD~1 同理.

Slide 24

git reset always moves the branch. The mode decides what happens to your files:

modestaging areaworking directory
--softkeptkept
--mixed (default)resetkept
--hardresetreset (changes lost!)

Example: undo the last commit, but keep its changes in your files:

$ git reset HEAD~1
Unstaged changes after reset:
M        test.txt

reset 一定会移动分支, 三种模式的区别只在「被撤掉的那次提交里的改动」放到哪:

  • --soft: 改动还在暂存区 (staged), 可以马上重新提交.
  • --mixed (默认, 不写就是它): 改动退回工作区 (modified), 暂存区清空.
  • --hard: 改动彻底丢掉, 工作区回到目标提交的样子. 最危险, 用前确认.

实测撤销最后一次提交后 git status --short 的结果: --soft 得 M  test.txt (M 在左栏, 已暂存), --mixed 得  M test.txt (M 在右栏, 未暂存), --hard 什么都没有. 例子 git reset HEAD~1 就是 mixed: 提交没了, 改动留在文件里.

本地基本流程
Basic workflow

Slide 25 
# Initalize an empty repository.
$ cd /path/to/repository
$ git init
# Create and stage a new README file.
$ vim README
$ git add README
$ git status # check the status of the repo.
# Commit the staged file with a commit-message.
$ git commit -m 'Initial commit'
# Edit the README and stage the changes to it.
$ vim README
$ git add README
$ git status # check the status of the repo.
# Commit the staged file with a commit-message.
$ git commit -m 'Update README'

把前面的命令串成一个完整的本地流程: init 建仓 → 新建文件 → add → status 确认 → commit; 之后每一轮都是「改 → add → status → commit」. vim 只是编辑文件的一种方式, 用 VS Code 或 PyCharm 编辑效果一样.

到这里所有操作都只发生在你自己的电脑上, 下一节才连接服务器.

远程分支: fetch、pull、push
Remote Branches · Fetching, pulling and pushing

Slide 31
  • reflect the state of the remote repository as of the last time you talked to it (they do not update automatically)
  • help understand difference between local work and published work
  • identified by <remote name>/<branch name>

clone 之后你电脑上有两个指针指向 f4265:

  • master: 你自己的本地分支, 你提交时它前进.
  • origin/master: 远程分支, 记录「上次和 origin 联系时, 服务器上的 master 在哪」. 它不会自动更新, 服务器那边有人提交了, 你这里的 origin/master 也不知道, 要 fetch 才更新.

比较 master 和 origin/master, 就知道哪些是只在你本地的工作、哪些已经发布到服务器上.

Slide 32
  • Fetch all the information from myremote: 
    $ git fetch myremote
* [new branch]  master  -> myremote/master
* [new branch]  dev     -> myremote/dev
    You now have a branch myremote/master that you can merge.
  • git pull: fetch and then merge into the current branch (commit your changes before pulling).
  • git push: push your commits to the remote (if the remote has commits you do not have, the push is rejected: pull first).
Slide 33
  • git fetch downloads the new commits and moves origin/master
  • your own files and your master are not changed
  • git fetch + git merge origin/master = git pull
Slide 34
  • git push uploads your new commits to the remote repository
  • your origin/master is updated automatically

三个同步命令, 按「改不改你的文件」区分:

命令做什么动你的 master 和文件吗
git fetch下载服务器上的新提交, 更新 origin/master不动. 只是「看看服务器上有什么」
git pullfetch, 再把 origin/master 合并进当前分支动, 相当于 fetch + merge
git push把你的新提交上传到服务器, origin/master 随之更新不动本地文件, 改的是服务器

读 Slide 33 的图: fetch 之前, 服务器上别人推了 31b8e、190a3; 你本地自己提交了 a38de、893cf. fetch 之后, 你本地的 origin/master 前进到 190a3, 你的 master 还在 893cf, 两条线从 f4265 分了叉. 这时 merge (或直接 pull) 会产生 Slide 21 里的合并提交.

读 Slide 34 的图: 这是另一种情况, 服务器在你 clone 之后没有新提交. 你的 a38de、893cf 可以直接接在服务器的 f4265 后面, push 成功. 如果像 Slide 33 那样服务器已经有你没有的提交, push 会被拒绝, 要先 pull.

易错: pull 之前先提交自己的改动, 否则合并可能会覆盖或卡住你没保存的工作.

冲突与远程工作流程
Resolving conflicts · Typical workflow with a remote

Slide 35

A conflict happens when both sides changed the same line. Git detects it when merging (e.g., during git pull):

$ git push
 ! [rejected]   master -> master (fetch first)
$ git pull
CONFLICT (content): Merge conflict in test.txt
Automatic merge failed; fix conflicts and then commit the result.
$ vim test.txt
<<<<<<< HEAD
Hello            # your version
=======
Hallo            # incoming version from the remote
>>>>>>> 1e40da2

Fix the file and delete the marker lines, then:

$ git add test.txt   # mark conflict as resolved
$ git commit         # commit message is pre-filled
$ git push

冲突: 两边改了同一行, Git 不知道该留哪个, 只好停下来让你决定. 改的是不同行, Git 会自动合好, 不算冲突.

完整经过 (已实测复现):

  1. push 被拒: (fetch first), 服务器上有你没有的提交.
  2. pull 时合并, 两边都改了 test.txt 的同一行, 报 CONFLICT.
  3. 打开文件, Git 在冲突处写了标记: <<<<<<< HEAD 到 ======= 之间是你的版本, ======= 到 >>>>>>> 之间是拉下来的版本.
  4. 手动改成你想要的最终内容 (留一个、或两者结合), 删掉三行标记.
  5. git add 告诉 Git「这个冲突解决了」, git commit (说明已自动填好), 再 git push.

幻灯片里 # your version 这类注释是讲解用的, 文件里并没有. 实际运行时, >>>>>>> 后面是对方那个提交的完整 40 位编号 (合并本地分支时则是分支名), 幻灯片缩写成了 7 位.

易错: 忘了删标记行就提交, 标记会原样进入代码, Python 文件直接报 SyntaxError.

Slide 36
  1. Get current project state from remote:
    • initially: clone project. 
      $ git clone git@github.com:username/projectname.git
    • later: fetch and merge changes from remote (possibly resolve conflicts) 
      git pull
  2. Make changes
    • add a File 
      $ git add CHANGES.txt
    • edit a File. 
      $ vim README.txt
  3. Stage and commit the changes locally. 
    git commit -a -m "Summary of changes."
  4. Fetch and merge changes from remote (possibly resolve conflicts) 
    git pull
  5. Push changes to remote. 
    git push

和小组一起做作业时的循环: pull → 改 → commit → pull → push.

  • 开工前先 pull, 拿到组员最新的版本, 冲突越少越好.
  • 第 3 步用 commit -a 时, 新文件 CHANGES.txt 已经在第 2 步单独 add 过了, 所以会被带上 (Slide 14 的规则).
  • push 前再 pull 一次: 期间组员可能又推了新提交, 不 pull 的话 push 会被拒.
